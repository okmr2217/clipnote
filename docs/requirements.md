# Clipnote 要件定義 v16

> 最終更新：2026-08-17（v16）
> ステータス：要件再定義完了（v12でクリップ削除をゴミ箱方式の論理削除に変更。v13では競合調査（hjarni）を踏まえた小規模拡張として、更新元の記録・コレクションのAI向けメタ情報連携を追加。v14ではv11でβ追加した一覧＋プレビューの2カラムレイアウトを標準レイアウトに昇格し、コレクション表示・複数行タイトル・操作メニューの整理を行った。v15ではMarkdownのYAML front matterへの対応状況を明確化し、`title`キーをタイトル自動取得の入力源に追加した上で、`title`以外のキー・値も本文閲覧時のメタデータ欄として表示するようにした。v16（本書）ではAIO/LLMO対策として、公開クリップ・コレクションを検索エンジン／AIクローラーが発見・引用しやすくする施策を追加した）
> 詳細設計（用語整理／ドメイン構成／UI方針／URL設計／セキュリティ設計／バリデーション／画面設計／データモデル／MCPサーバー設計）は別紙「Clipnote設計書 v18」、ゴミ箱機能の詳細は`docs/design-trash.md`を参照

**v16（本書）での変更点**：AIO（AI Overviews等の生成的検索結果）・LLMO（ChatGPT/Perplexity等のLLM系クローラー・回答エンジン向け最適化）対策として、公開（`public`）なクリップ・コレクションに限定した以下の施策を追加した（17章、設計書`docs/design-web.md`4-9節）。①`robots.txt`・`sitemap.xml`を新設し、公開クリップ・コレクションのURLをsitemapに列挙。②本文（別オリジンのsandboxed iframeで配信するため、JSを実行しないクローラーには通常見えない）のプレーンテキスト版を`/p/[uuid]`自体に`sr-only`で埋め込み。③`/p/[uuid]`・`/c/[uuid]`・LPにJSON-LD構造化データを追加。④LPのメタデータ（title・description・OGP等）を強化。private側の秘匿性（11章のOGP方針等）は変更しない。

**v15での変更点**：Markdownのfront matter（`---`で囲まれたYAMLメタデータブロック）について、従来は未定義（未対応）だった状況を整理し、次の対応を追加した。①管理画面のタイトル自動取得（5-4節、設計書`docs/design-web.md`5-4節）で、本文先頭のfront matterに`title`キーがあれば最優先で採用する（無ければ従来通りH1にフォールバック）。②`apps/content`のMarkdownレンダリングパイプラインに`remark-frontmatter`を追加し、front matterブロックが本文としてそのまま表示されてしまう不具合を修正した（設計書`docs/design-content.md`4章）。③front matterの`title`以外の全キー・値を、本文冒頭のメタデータ欄として閲覧時に表示するようにした（設計書`docs/design-content.md`4章）。`title`のみDBの`pages.title`カラムに反映され、それ以外のキーはDBには保存されず表示のみ（`description`・`tags`用の専用カラムを新設するものではなく、タグ機能は5-7節で引き続きMVP対象外）。値の意味解釈（Markdown/HTMLとしてのレンダリング等）は行わず、常にプレーンテキストとして表示する。MCPの`upload_page`は従来通り`title`引数が必須のままで、front matterからの自動抽出はしない（5-9節）。

**v10での変更点**：クリップ管理機能の拡張方針検討（お気に入り・グループ・タグ・インラインプレビュー等を含む）のうち、まず**固定機能**（一覧の並び順を「固定クリップ→更新日時降順」の2段構成にする、非破壊的なトグル）と**アーカイブ機能**（一覧のデフォルト表示から外すが削除はしない、非破壊的なトグル）を追加した（5-1節・5-8節・9章・13章）。お気に入り・タグ・2カラムのリッチな一覧UIは別途検討中、グループ機能はコレクション（`private`設定での非公開整理）に役割が吸収されるため見送りとした。

**v11での変更点**：v10で検討中としていた**一覧＋プレビューの2カラムレイアウト**を、既存の`/admin`（テーブル/カード一覧）と並行稼働するβ版として`/admin/clips`に追加した（5-8節）。既存の一覧はそのまま残し、双方向にリンクして行き来できるようにした上で、今後の判断（置き換え／併存）に備える。

**v14（本書）での変更点**：v11でβ追加した一覧＋プレビューの2カラムレイアウトを、`/admin`の標準レイアウトに昇格した（旧来のテーブル/カード一覧は廃止）。あわせて、一覧行にコレクションチップ・複数行タイトル表示を追加し、増えてきたクリップ操作（固定・コンテンツ更新・メタデータ編集・アーカイブ・削除）を「固定」ボタン＋オーバーフローメニューに整理した。モバイルも同じレイアウトのため、一覧タップで管理画面内のプレビューに切り替わる（旧UIのような公開ページへの外部遷移はなくなった）（5-8節）。

**v12での変更点**：競合調査（Hjarni）で指摘された「削除の救済手段がない」ギャップに対応し、クリップの**「削除」を即時物理削除からゴミ箱方式の論理削除に変更した**（5-1節・9章・10章。詳細は`docs/design-trash.md`）。削除は`pages.deleted_at`を立てるだけの非破壊操作になり確認ダイアログ不要（Undoトースト方式）、30日間は`/admin/trash`から復元できる。30日経過後は日次バッチで自動的に完全削除（物理削除）される。「完全に削除」の手動操作のみ確認ダイアログを必須とする。

**v13（本書）での変更点**：同じ競合調査（hjarniのバージョン管理・フォルダ単位のAI指示機能）で優先度「中」「低」として挙げていた2点を追加した。①`page_versions`に更新元（`web` / `api_key` / `oauth`）を記録する`source`列を追加し、更新履歴画面にバッジ表示（5-4節・9章）。②MCPの`get_page`の返り値に、所属コレクションの名前・説明を読み取り専用で追加し、AIがクリップの文脈（どのコレクションに属すか）を踏まえた更新を行えるようにした（5-9節）。優先度「高」（クリップ削除の猶予期間）はv12で対応済み。

## 1. プロダクト概要

**Clipnote**は、HTML・Markdown・プレーンテキスト形式のコンテンツを管理・閲覧するためのツール。Markdownの代替として、より表現力の高いHTML文書を保存・共有すること、および装飾のないメモ書きや会話ログをそのまま残せることを主目的とする。

ユーザー向けには、個別のHTML/Markdown/プレーンテキスト文書を「**クリップ**」と呼称する（DB上のテーブル名・URLパスは引き続き`pages`/`/p/`を使用。詳細は設計書0章）。

### 基本的な利用フロー

1. 管理画面から、またはMCP対応クライアント（Claude等）からHTML・Markdown・プレーンテキストいずれかのコンテンツを登録
2. 公開設定（`private` / `public`）を行う
3. 個別クリップ、または複数クリップをまとめた「コレクション」のURLを公開できる
4. ブラウザから閲覧（本人は管理画面経由、他者は公開URL経由）

### ユーザー獲得（LP）の訴求ポイント

- AIとの会話で生成させたHTML/Markdown、あるいは会話ログやメモ書きをそのまま保存して管理・閲覧できる
- **AI（Claude等）との会話から直接クリップを作成・更新できる（MCP連携、v6で追加）**
- HTML/Markdown/プレーンテキストのコンテンツにユニークな公開URLを発行して共有できる
- 複数のコンテンツをコレクションとしてまとめて管理・公開できる

## 2. ユーザー

| フェーズ | 内容 |
| --- | --- |
| 認証（Web） | better-auth（メール/パスワード方式） |
| 認証（MCP、v6で追加） | APIキー方式。ユーザーが管理画面から発行・失効できる |
| 認証（MCP、v7で追加） | OAuth 2.1方式（Authorization Code + PKCE + 動的クライアント登録）。APIキー方式と併存し、いずれもWebのログインセッションと同じ`users`テーブルを参照する |

- 各ユーザーは自分のクリップ・コレクション・APIキー・OAuth連携のみ管理画面で編集できる

- v7で追加したOAuth 2.1は、あくまでMCP（`mcp.clipnote.paritto.dev`）向けの認可サーバーとしてClipnote単体で完結させる。別リポジトリ`paritto-auth`が担うエコシステム全体（Paritto）のSSO統合は引き続き将来検討とし、混同しないこと（16章参照）

## 4. 対応コンテンツ形式

| 形式 | 保存方式 | 表示方式 |
| --- | --- | --- |
| HTML | そのまま保存 | 別ドメインiframeでレンダリング |
| Markdown | そのまま保存（ソース） | 別ドメインiframeでレンダリング（unified/remark/rehypeビューワー経由） |
| **プレーンテキスト（v9で追加）** | **そのまま保存** | **別ドメインiframeでレンダリング（構文はいっさい解釈せず、改行・空白を保持したまま表示）** |

保存されるHTML/Markdownは無害化（サニタイズ）処理を行わない。プレーンテキストは構文を解釈しない形式のため、表示時にHTML特殊文字をエスケープするが、これは危険なコンテンツを除去する無害化とは異なる（元々実行される余地がない）。管理画面経由・MCP経由いずれの登録でも同じ方針とする。

## 5. 機能要件

### 5-1. クリップ管理

- クリップの**新規作成**（管理画面のダイアログ、または**MCP経由の`upload_page`、v6で追加**）
- クリップ本文の**更新（全文差し替え）**（管理画面のダイアログ、または**MCP経由の`update_page`、v6で追加**）
- クリップのメタデータ（タイトル・公開設定・所属コレクション）の**編集**（管理画面のみ）
- クリップの**削除**（管理画面のみ。MCP経由の削除は対象外）：**v12でゴミ箱方式の論理削除に変更**。「削除」は`pages.deleted_at`を立てるだけの非破壊操作で、即時反映・確認ダイアログ不要（Undoトースト方式）。ゴミ箱（`/admin/trash`）から30日以内なら「復元」できる。30日経過後は自動的に、またはゴミ箱からの「完全に削除」操作（確認ダイアログ必須、唯一の不可逆操作）で物理削除される。詳細は`docs/design-trash.md`
- クリップの**公開設定**（クリップ単位：`private` / `public`）
- クリップの**固定**（v10で追加、管理画面のみ）：一覧の並び順を「固定クリップを先頭・固定クリップ内は更新日時降順、それ以外は更新日時降順」に変える、状態のみのトグル。即時反映・確認ダイアログ不要（何度でも戻せるため）
- クリップの**アーカイブ**（v10で追加、管理画面のみ）：一覧のデフォルト表示から外すが、クリップ自体・更新履歴・所属コレクションは保持する。削除とは明確に区別し、いつでもアーカイブ解除できる。即時反映・確認ダイアログ不要

### 5-2. 新規作成・本文更新の入力方式（管理画面）

- **貼り付け**：管理画面のダイアログ内テキストエリアに全文をペースト
- **ファイルから読み込み**：ファイルを選択またはドラッグ&ドロップすると、サーバーへアップロードせずクライアント側でファイル内容とファイル名を読み取り、本文・タイトルの初期値へ即時反映する

### 5-3. コンテンツバリデーション

- HTML/Markdownとしての厳密な構文検証は行わない（プレーンテキストはそもそも構文を持たないため対象外）。空文字列・不正なUTF-8エンコーディングのみを拒否する
- 本文サイズの上限は**1MB（1,048,576 bytes、UTF-8換算）**とし、クライアント側・サーバー側の両方でチェックする
- **管理画面経由・MCP経由いずれのバリデーションも共通のロジックを使用する（v6で明確化）**

### 5-4. 更新履歴・バージョン管理

- 本文更新のたびに、更新前のバージョンを履歴として保存する
- 直近**10件**のバージョンを保持する
- 過去のバージョンをプレビューし、任意のバージョンへ**復元**できる
- 現在のバージョン・過去のバージョンいずれも、ファイルとしてダウンロードできる。復元は過去のバージョンにのみ提供する
- **MCP経由の`update_page`による更新も、管理画面と同じ`page_versions`退避ロジックを通る（v6で明確化）**
- **更新元（管理画面／MCP・APIキー／MCP・OAuth）を`page_versions.source`に記録し、更新履歴画面にバッジ表示する（v13で追加）**

### 5-5. 閲覧

- 公開URL `/p/[uuid]` でコンテンツをレンダリング
- `private`クリップは認証必須（かつ自分のクリップのみ）
- `public`クリップは認証なしで誰でも閲覧可
- 管理画面内でもプレビュー表示

### 5-6. コレクション管理

- 管理画面から作成・編集・削除
- コレクションは「クリップの一覧ページ」として機能する
- コレクションには名前・説明を持つ
- 1クリップが複数コレクションに属せる（多対多）
- コレクションには専用の一覧ページ `/c/[uuid]` が生成される
- コレクション自体も公開設定（`private` / `public`）を持つ
- 公開コレクションに非公開クリップが含まれる場合、そのクリップは一覧表示から除外する
- 所有者本人が認証済みで閲覧する場合は、公開設定を問わず全所属クリップを表示する
- 所属クリップの**並び替え**が可能（デスクトップはドラッグ&ドロップ、モバイルは並び替えモード＋上下移動ボタン）
  - **デスクトップ：ドラッグ中はドロップ予定位置にプレースホルダーを表示。ドロップ確定時に1回のAPIコールで一括送信（v6で明確化）**
  - **モバイル：並び替えモード中の移動はローカル状態のみ反映し、「完了」押下時に1回のAPIコールで一括送信。「完了」を押さずに画面を離れた場合は変更を破棄する（v6で確定）**
- 所属クリップの**追加**は、自分の全クリップから検索・複数選択するダイアログで行う
  - **一覧は更新日時の新しい順、検索はタイトル部分一致、各行に形式バッジを表示する（v6で確定）**
- コレクションから「**外す**」（関連付けの解除のみ、クリップ自体は残る）と、クリップ自体の「**削除**」は明確に別操作として区別する
- **新規作成完了後は詳細画面へ自動遷移し、「クリップを追加」ダイアログを開いた状態にする（v6で確定。作成と追加の往復を削減する導線）**
- **コレクション一覧では、行クリックで詳細画面へ遷移する（クリップ一覧の「クリックでプレビュー」とは非対称。v6で確定）**
- **コレクション詳細画面には、公開URLコピーと「公開ページで見る」リンクを表示する（v6で追加）**

### 5-7. タグ管理

MVP対象外として確定。コレクションのみでの分類とし、フィルタリング・検索が必要になった段階で次フェーズとして追加する。

### 5-8. 管理画面

- **認証**：better-auth（メール/パスワード、サインアップ・ログイン）
- **クリップ一覧＋プレビュー（`/admin`、v11でβ追加・v14で標準レイアウトに昇格）**：一覧＋プレビューの2カラムレイアウト。左に軽量な索引（固定→更新日時降順、固定クリップは「固定」セクションにまとめる。形式・タイトル（複数行表示、v14で追加）・固定有無・公開設定（色ドット）・更新日時・**所属コレクションのチップ（v14で追加）**。**行の右端の「⋯」メニューから「公開にする」／「非公開にする」を選び、選択せずに一覧から直接切り替えられる（v14で追加。直接タップできるボタンにはせず、メニュー操作にすることで誤操作を防ぐ）**）、右に選択したクリップの本文プレビューと操作（公開設定切替・コレクション表示・公開URLコピー・更新履歴に加え、「固定・固定解除」ボタンと、メタデータ編集・コンテンツ更新・アーカイブ・削除をまとめたオーバーフローメニュー、**v14で操作を整理**）を表示する。モバイル（`md`未満）は1カラムに切り替わり、一覧タップで右ペイン（管理画面内のプレビュー）に全画面切り替えする（**v14でモバイルにも対応。公開ページへの外部遷移は発生しない**）
- **クリップ詳細**：コンテンツプレビュー、更新履歴の確認・復元、所属コレクションの確認、公開設定の変更
- **新規作成・メタデータ編集・本文更新**：いずれもダイアログで完結
- **コレクション一覧**：コレクション名・説明・公開設定・所属クリップ数。**行クリックで詳細画面へ遷移。オーバーフローメニューは「編集」「削除」のみ。説明未入力は「説明なし」表示（v6で確定）**
- **コレクション詳細**：コレクション情報・公開設定の編集、所属クリップの追加・削除・並び替え、**公開URLコピー・公開ページへのリンク（v6で追加）**
- **APIキー管理（v6で追加）**：`/admin/api-keys`にて、名前を付けてのAPIキー発行（発行直後のみ生キー全文を表示）・一覧（マスク表示、最終利用日時）・失効を管理
- **削除**（クリップ・コレクション・APIキーそれぞれ）

画面設計の詳細は設計書v13 6章・7章・8章を参照。

### 5-9. MCPサーバー（v6で新規追加）

MCP対応クライアント（Claude Desktop、Claude Code等）から、Clipnoteのクリップを直接操作できる機能。`mcp.clipnote.paritto.dev`で稼働。

| ツール | 内容 |
| --- | --- |
| `list_pages` | 自分のクリップ一覧を取得（タイトル検索対応、本文は含まない） |
| `get_page` | 指定uuidのクリップを本文込みで取得。**所属コレクションのid・名前・説明も付随情報として返す（v13で追加）** |
| `upload_page` | 新規クリップを作成（content・content_type・title・visibility） |
| `update_page` | 既存クリップの本文を全文差し替え |

- 認証はAPIキー（Bearerトークン）方式、またはOAuth 2.1方式（Authorization Code + PKCE + 動的クライアント登録、v7で追加）のいずれか。前者は8章のAPIキー管理画面で発行したキーを使用し、Claude Desktop・Claude Code等の直接Bearerトークンを設定できるクライアント向け。後者はclaude.aiのカスタムコネクタ等、OAuthの動的クライアント登録が前提のクライアント向けで、既存のWebログインセッションでの認可＋同意画面（`/oauth/consent`）を経て発行する
- OAuthで連携したアプリは、`/admin/api-keys`内の「連携中のアプリ」から確認・失効できる（v7で追加）
- `upload_page`時点でのコレクションへの割当は行わない（管理画面から手動で割り当てる運用）。**`get_page`でのコレクション情報の付随取得（v13で追加）はあくまで読み取り専用であり、この方針を変えるものではない**
- クリップの削除、コレクションの作成・編集はMCP経由では対象外（将来検討）
- **`update_page`実行時、`page_versions`へ退避する行にこの接続の認証方式（APIキー／OAuth）を`source`として記録する（v13で追加、5-4節）**

詳細は設計書v13 13章を参照。

### 5-10. アカウント管理（v8で新規追加）

better-authのコア機能（追加プラグイン不要）で実現する、ログイン以外のアカウント関連機能。

| 機能 | 内容 |
| --- | --- |
| パスワードリセット | `/forgot-password`でメールアドレスを入力→再設定用リンクをメール送信→`/reset-password`で新パスワードを設定。メールアドレスの登録有無に関わらず同じ成功メッセージを表示し、登録有無の推測（ユーザー列挙）を防ぐ |
| メール確認 | サインアップ時に確認メールを自動送信。**任意**（未確認でもクリップ作成・閲覧等の機能は制限しない）。`/admin`配下に未確認バッジ＋再送信ボタンのバナーを表示 |
| パスワード変更 | ログイン中ユーザーが現在のパスワードを入力した上で変更。変更時は他端末のセッションを無効化する |
| アカウント設定画面 | `/admin/settings`。名前・メールアドレス・メール確認状態を表示し、パスワード変更はダイアログで行う（設計書0章・6章・7章のダイアログ方針に準拠） |

メール送信はCloudflare Email Service（`send_email`バインディング）を使用。送信元ドメイン（`paritto.dev`）のEmail Sending有効化はCloudflareアカウントに対する手動作業として別途実施する。未有効化の間・開発環境では、メールを実送信せずリンクをサーバーログに出力するフォールバックで動作する。

詳細は設計書v13 16章を参照。

## 6. URL設計（概要）

`/p/[uuid]`（個別クリップ）、`/c/[uuid]`（コレクション一覧）、`/admin`配下（管理画面）、`/admin/api-keys`（APIキー管理・連携中のアプリ管理、v6で追加、v7でOAuth連携管理を追加）、`/admin/settings`（アカウント設定、v8で追加）、`/forgot-password`・`/reset-password`（パスワードリセット、v8で追加）、`/oauth/consent`（OAuth同意画面、v7で追加）、`/login`・`/signup`の構成。MCPサーバー側にも`/.well-known/oauth-protected-resource`（v7で追加）がある。詳細は**Clipnote設計書v13 3章**を参照。

## 7. UI／UXデザイン方針（概要）

管理画面（APIキー管理含む）はshadcn/ui + Tailwind CSSでCRUD作業に適した構成とし、LP・公開ページのiframe外枠はブランド訴求を重視したカスタムTailwind実装とする。詳細は**Clipnote設計書v13 2章**を参照。

---

## 8. セキュリティ設計（概要）

コンテンツは別ドメインからiframe配信し、sandbox属性で実行コンテキストを隔離する。Web認証は署名付き短命トークン（HMAC-SHA256）、**MCP認証はAPIキー（ハッシュ化して保存、Bearerトークンとして検証、v6で追加）とOAuth 2.1（JWTアクセストークンをJWKSでローカル検証、v7で追加）を併存させる**。詳細は**Clipnote設計書v13 4章**を参照。

---

## 9. データモデル（概要）

`pages`・`collections`・`collection_pages`・`page_versions`・**`api_keys`（v6で追加）**・**`jwks`・`oauth_clients`・`oauth_access_tokens`・`oauth_refresh_tokens`・`oauth_consents`（v7で追加）**を中心に構成する。**`pages`には固定機能・アーカイブ機能用に`pinned`（真偽値、既定`false`）・`archived_at`（nullable timestamp）を追加した（v10で追加）。ゴミ箱機能用に`deleted_at`（nullable timestamp）を追加した（v12で追加。詳細は`docs/design-trash.md`）。**`api_keys`は名前・キーのハッシュ値・マスク表示用プレフィックス・最終利用日時を持ち、ユーザー削除時に連動削除する。OAuth関連テーブルはbetter-authの`jwt`・`oauthProvider`プラグインが管理し、`apps/web`のみが読み書きする。**`page_versions`には更新元記録用に`source`（enum：`web` / `api_key` / `oauth`、既定`web`）を追加した（v13で追加）。**詳細は**Clipnote設計書v13 12章**を参照。

---

## 10. 削除時のカスケード挙動

**クリップの「削除」は、v12（本書）でゴミ箱への論理削除に変更した**（詳細は`docs/design-trash.md`）。30日間はゴミ箱から復元でき、期間経過後または「完全に削除」操作で初めて下表の物理削除が発生する。

| 削除対象 | 影響範囲 |
| --- | --- |
| クリップをゴミ箱から完全に削除（30日経過後の自動パージ、または手動操作） | 更新履歴（`page_versions`）も連動削除。所属していた全コレクションから自動的に外れる（コレクション自体は残る） |
| コレクションを削除 | クリップとの関連付けのみ削除。所属していたクリップ自体は削除されない |
| **APIキーを失効（v6で追加）** | **`api_keys`行を削除。以降そのキーでのMCP認証は失敗する** |
| **連携中のアプリを失効（v7で追加）** | **該当ユーザー×クライアントの`oauth_consents`・`oauth_refresh_tokens`・`oauth_access_tokens`行を削除。既発行のアクセストークンは有効期限切れまで有効** |

## 11. 公開URLのシェア表示（OGP）

- publicなクリップ／コレクションは、タイトル・説明を`og:title` / `og:description`として出力する
- privateなクリップ／コレクションは、タイトルや説明などの固有情報をOGPに出力しない

---

## 12. 短命トークンの失効対策

コンテンツ配信の認証トークンは有効期限2分のため、`/p/[uuid]`・`/c/[uuid]`の親ページ側で90秒間隔でトークンを再取得し、iframeの`src`を書き換える。

---

## 13. 確認ダイアログの基準

破壊性・復元可能性に応じて確認ダイアログの要否を統一する。公開設定のトグル・メタデータ編集・「外す」操作・バージョンのダウンロード・**クリップの固定/固定解除（v10で追加）**・**クリップのアーカイブ/アーカイブ解除（v10で追加）**・**クリップの削除＝ゴミ箱への移動、ゴミ箱からの復元（v12で変更。30日間は可逆なため確認不要、Undoトースト方式）**は確認不要。コンテンツ更新・バージョン復元・コレクション削除・**APIキーの失効（v6で追加）**・**連携中のアプリの失効（v7で追加）**・**ゴミ箱からの完全削除（v12で追加。唯一の不可逆操作）**は確認ダイアログを必須とする。詳細は設計書v13 10章・`docs/design-trash.md`4章を参照。

## 17. AIO/LLMO対策（v16で追加）

検索エンジンのAI Overviews・ChatGPT/Perplexity等のLLM系クローラー・回答エンジンに、公開クリップ・コレクションを発見・引用してもらうための対策。**publicなクリップ・コレクションのみを対象とし、privateの秘匿性（11章のOGP方針等）は一切変更しない**。

- `robots.txt`・`sitemap.xml`を新設し、公開クリップ・コレクションのURL、およびLP・お問い合わせ等の静的ページを列挙する。管理画面・API・認証系ページはクロール対象から除外する
- 公開クリップの本文は、XSS隔離のため別オリジンのsandboxed iframe（1章・8章）で配信しており、JavaScriptを実行しないクローラーには通常見えない。この制約下でも本文を発見できるよう、プレーンテキスト化した本文を`/p/[uuid]`自体に視覚上非表示（スクリーンリーダー用領域）で埋め込む
- `/p/[uuid]`・`/c/[uuid]`・LPに構造化データ（JSON-LD）を出力し、AIによる情報抽出の精度を高める
- LPのメタデータ（タイトル・説明文・OGP等）を強化し、Clipnoteというツール自体をAIが正確に説明・推薦できるようにする

詳細は設計書v18`docs/design-web.md`4-9節を参照。
