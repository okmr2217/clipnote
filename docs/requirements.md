## 1. プロダクト概要

**Clipnote**は、HTMLおよびMarkdown形式のコンテンツを管理・閲覧するためのツール。Markdownの代替として、より表現力の高いHTML文書を保存・共有することを主目的とする。

ユーザー向けには、個別のHTML/Markdown文書を「**クリップ**」と呼称する（DB上のテーブル名・URLパスは引き続き`pages`/`/p/`を使用。詳細は設計書0章）。

### 基本的な利用フロー（MVP）

1. 管理画面からHTMLまたはMarkdownコンテンツを直接登録（貼り付け、またはファイルから読み込み）
2. 公開設定（`private` / `public`）を行う
3. 個別クリップ、または複数クリップをまとめた「コレクション」のURLを公開できる
4. ブラウザから閲覧（本人は管理画面経由、他者は公開URL経由）

> MCP経由でのAI（Claude等）からの直接アップロードは次フェーズで対応する。MVPでは管理画面からの手動登録のみ。

### ユーザー獲得（LP）の訴求ポイント

- AIとの会話で生成させたHTML/Markdownを、そのまま保存して管理・閲覧できる
- HTML/Markdownのコンテンツにユニークな公開URLを発行して共有できる
- 複数のコンテンツをコレクションとしてまとめて管理・公開できる

LPは管理画面とは別のデザイン方針（カスタムTailwind、詳細は設計書2章）で制作し、上記の価値訴求を軸に構成する。

## 2. ユーザー

MVPからマルチユーザー対応を含める。

| フェーズ | 内容 |
| --- | --- |
| MVP | 複数ユーザーが各自アカウントを持ち、自分のコンテンツ・コレクションを管理する |
| 認証 | better-auth（メール/パスワード方式） |

- 各ユーザーは自分のクリップ・コレクションのみ管理画面で編集できる
- 公開設定された（`public`の）クリップ・コレクションは、ログインなしで誰でも閲覧できる
- OAuth 2.1 Providerとしてのエコシステム統合は将来検討とし、MVPでは単体アプリとしての認証にとどめる

## 3. 技術スタック・インフラ構成

| 項目 | 技術 |
| --- | --- |
| フロントエンド／API | Next.js (App Router) + TypeScript |
| ホスティング（本体） | Cloudflare Worker（`@opennextjs/cloudflare`アダプタ経由でデプロイ） |
| UIコンポーネント（管理画面） | shadcn/ui + Tailwind CSS |
| UIデザイン（LP・公開ページ外枠） | カスタム実装（Tailwind CSS） |
| DB | Cloudflare D1（ネイティブバインディングでアクセス） |
| コンテンツ配信 | 別ドメイン、Cloudflare Worker |
| 認証 | better-auth（メール/パスワード方式） |
| MCP | 次フェーズで対応。Cloudflare Workerとして構築予定（本書のスコープ外） |

技術スタックをフルCloudflare化した理由：本体・コンテンツ配信・将来のMCPサーバーが同一アカウント内のWorkerで統一されることで、D1へのネイティブバインディングアクセスが可能になり、将来Service Bindingsによる直接RPC接続も見込める。

### ドメイン構成（v4で確定）

| 用途 | ドメイン |
| --- | --- |
| Web本体（管理画面／公開ページ外枠／LP） | `clipnote.paritto.dev` |
| コンテンツ配信（iframe内） | `content.clipnote.paritto.dev` |
| MCPサーバー（次フェーズ） | `mcp.clipnote.paritto.dev` |

いずれも`paritto.dev`配下のサブドメインとして運用する。別ドメイン新規取得によるドメイン間の完全分離は行わないため、セッションCookieのスコープ設定（`Domain`属性をホスト単体に限定）が多層防御の実効性を左右する。詳細は設計書1章を参照。

### リポジトリ構成（v6で追加）

モノレポとし、`apps/web`（本体）・`apps/content`（コンテンツ配信）・`apps/mcp`（MCP、次フェーズ）と、共有ロジックの`packages/db`・`packages/content-token`で構成する。詳細は設計書12章を参照。

**留意点（実装時に確認）**
- `@opennextjs/cloudflare`はNode.js runtimeが前提（Edge runtime不可）
- Workerのバンドルサイズ上限（Free: 3MiB / Paid: 10MiB）。依存ライブラリ増加時は要計測
- 画像最適化機能（`next/image`）はMVPでは無効のまま運用する想定（IMAGES binding要・追加コスト発生のため）
- Cloudflare D1の行サイズ上限（2MB）を踏まえたコンテンツサイズ制限を設ける（5-7節）

## 4. 対応コンテンツ形式

| 形式 | 保存方式 | 表示方式 |
| --- | --- | --- |
| HTML | そのまま保存 | 別ドメインiframeでレンダリング |
| Markdown | そのまま保存（ソース） | 別ドメインiframeでレンダリング（unified/remark/rehypeビューワー経由） |

保存されるHTML/Markdownは無害化（サニタイズ）処理を行わない。iframeの別ドメイン配信・sandbox属性による実行コンテキストの隔離によって安全性を担保する設計とする（詳細は設計書4章）。

## 5. 機能要件

### 5-1. クリップ管理

- クリップの**新規作成**（管理画面のダイアログから、貼り付け or ファイル読み込み）
- クリップ本文の**更新（全文差し替え）**（管理画面のダイアログから、貼り付け or ファイル読み込み）
- クリップのメタデータ（タイトル・公開設定・所属コレクション）の**編集**
- クリップの**削除**（管理画面から）
- クリップの**公開設定**（クリップ単位：`private` / `public`）

> クリップ本文のインライン編集（エディタ＋ライブプレビュー）はMVP対象外（10章参照）。本文の更新は全文差し替えのみに対応する。

### 5-2. 新規作成・本文更新の入力方式

- **貼り付け**：管理画面のダイアログ内テキストエリアに全文をペースト
- **ファイルから読み込み**：ファイルを選択またはドラッグ&ドロップすると、**サーバーへアップロードせずクライアント側でファイル内容とファイル名を読み取り**、本文・タイトルの初期値へ即時反映する。バックエンドへ送信するのは、貼り付け・ファイルいずれの経路でも本文の文字列＋メタデータのみで、単一のAPI経路に統一する

形式（HTML/Markdown）は内容または拡張子から自動判定し、手動での上書きも可能とする。

### 5-3. コンテンツバリデーション

- HTML/Markdownとしての厳密な構文検証は行わない（AIが生成する断片的なマークアップを許容するため）。空文字列・不正なUTF-8エンコーディングのみを拒否する
- 本文サイズの上限は**1MB（1,048,576 bytes、UTF-8換算）**とし、クライアント側・サーバー側の両方でチェックする（Cloudflare D1の行サイズ上限2MBに対する安全マージン）
- ファイル読み込み時は、拡張子・簡易的な文字化け検知により警告を行う（ブロックはしない）

詳細は設計書5章を参照。

### 5-4. 更新履歴・バージョン管理（v4でMVP対象に追加）

- 本文更新のたびに、更新前のバージョンを履歴として保存する
- 直近**10件**のバージョンを保持する
- 過去のバージョンをプレビューし、任意のバージョンへ**復元**できる
- 復元操作自体も1回の更新として履歴に記録される（復元の取り消しが可能）
- **現在のバージョン・過去のバージョンいずれも、ファイルとしてダウンロードできる（v5で追加）**。復元は過去のバージョンにのみ提供する。ダウンロードはクリップ本文のインライン編集機能を持たない設計を補完する役割も持ち、「ダウンロード→手元で編集→コンテンツ更新で再登録」という運用を想定する

詳細は設計書6-5章・11章（`page_versions`テーブル）を参照。

### 5-5. 閲覧

- 公開URL `/p/[uuid]` でコンテンツをレンダリング
- `private`クリップは認証必須（かつ自分のクリップのみ）
- `public`クリップは認証なしで誰でも閲覧可
- 管理画面内でもプレビュー表示

### 5-6. コレクション管理

- 管理画面から作成・編集・削除
- コレクションは「クリップの一覧ページ」として機能する
- コレクションには名前・説明を持つ
- 1クリップが複数コレクションに属せる（多対多）
- コレクションには専用の一覧ページ `/c/[uuid]` が生成される
- コレクション自体も公開設定（`private` / `public`）を持つ
- 公開コレクションに非公開クリップが含まれる場合、そのクリップは一覧表示から**除外**する（存在自体を見せない。ロック表示はしない）
- 所有者本人が認証済みで閲覧する場合は、公開設定を問わず全所属クリップを表示する
- 所属クリップの**並び替え**が可能（デスクトップはドラッグ&ドロップ、モバイルは並び替えモード＋上下移動ボタン。v5で追加）
- 所属クリップの**追加**は、自分の全クリップから検索・複数選択するダイアログで行う（v5で追加）
- コレクションから「**外す**」（関連付けの解除のみ、クリップ自体は残る）と、クリップ自体の「**削除**」は明確に別操作として区別する（v5で追加）

詳細は設計書7章を参照。

### 5-7. タグ管理

MVP対象外として確定。コレクションのみでの分類とし、フィルタリング・検索が必要になった段階で次フェーズとして追加する。

### 5-8. 管理画面

- **認証**：better-auth（メール/パスワード、サインアップ・ログイン）
- **クリップ一覧**：形式・タイトル・公開設定・所属コレクション・更新日時・公開URLコピー。デスクトップはテーブル形式、モバイル（`md`未満）はカード形式に切り替える。更新順で表示
- **クリップ詳細**：コンテンツプレビュー、更新履歴の確認・復元、所属コレクションの確認、公開設定の変更
- **新規作成・メタデータ編集・本文更新**：いずれもダイアログで完結（専用ページは設けない）。新規作成と本文更新は同じ入力UI（貼り付け／ファイル統合欄）を再利用しつつ、本文更新は破壊的操作として警告文・サイズ差分表示を伴う
- **コレクション一覧**：コレクション名・説明・公開設定・所属クリップ数。更新順で表示
- **コレクション詳細**：コレクション情報・公開設定の編集、所属クリップの追加・削除・並び替え（ドラッグ&ドロップ）
- **削除**（クリップ・コレクションそれぞれ）

画面設計の詳細（レイアウト案・ダイアログ構成）は設計書6章を参照。

> APIキー管理画面はMVP対象外（MCP対応時に追加）

## 6. URL設計（概要）

`/p/[uuid]`（個別クリップ）、`/c/[uuid]`（コレクション一覧）、`/admin`配下（管理画面）、`/login`・`/signup`の構成。詳細は**Clipnote設計書 3章**を参照。

## 7. UI／UXデザイン方針（概要・v4で追加）

管理画面はshadcn/ui + Tailwind CSSでCRUD作業に適した構成とし、LP・公開ページ（`/p/` `/c/`）のiframe外枠はブランド訴求を重視したカスタムTailwind実装とする。iframe内部（ユーザー生成コンテンツ）はデザインシステムの対象外。詳細は**Clipnote設計書 2章**を参照。

---

## 8. セキュリティ設計（概要）

マルチユーザー対応に伴い、コンテンツは別ドメイン（`content.clipnote.paritto.dev`）からiframe配信し、`sandbox="allow-scripts allow-popups allow-modals allow-popups-to-escape-sandbox"`で実行コンテキストを隔離する。認証は署名付き短命トークン（HMAC-SHA256）を用いる。公開コレクション内の非公開クリップはフィルタリングして非表示にする。コンテンツ本体への無害化（サニタイズ）処理は行わない。詳細は**Clipnote設計書 4章**を参照。

---

## 9. データモデル（概要）

`pages`・`collections`・`collection_pages`・`page_versions`の4テーブルを中心に構成し、`collections`には`visibility`カラムを持たせる。`page_versions`はv4で新規追加し、本文更新のたびに旧バージョンを退避、直近10件を保持する。`collection_pages`・`page_versions`の外部キーには`ON DELETE CASCADE`を設定し、削除時の整合性をDB制約で担保する。`tags`関連・`api_keys`は将来テーブルとして扱う。詳細は**Clipnote設計書 11章**を参照。

---

## 10. 削除時のカスケード挙動（v5で追加）

| 削除対象 | 影響範囲 |
| --- | --- |
| クリップを削除 | 更新履歴（`page_versions`）も連動削除。所属していた全コレクションから自動的に外れる（コレクション自体は残る） |
| コレクションを削除 | クリップとの関連付けのみ削除。**所属していたクリップ自体は削除されない** |

コレクション削除時の確認ダイアログには「所属していたクリップ自体は削除されません」という文言を明記し、誤解を防ぐ。詳細は設計書8章を参照。

---

## 11. 公開URLのシェア表示（OGP）（v5で追加）

公開URLのシェアはユーザー獲得導線の一部であるため、SNSやチャットでの見え方を定義する。

- publicなクリップ／コレクションは、タイトル・説明を`og:title` / `og:description`として出力する。`og:image`は当面固定のブランド画像とする
- privateなクリップ／コレクションは、タイトルや説明などの固有情報をOGPに出力しない（非公開情報の秘匿性を保つため）
- 将来、一覧サムネイル機能（13章）の実装後、`og:image`を動的なプレビュー画像に差し替える

詳細は設計書4-6節を参照。

---

## 12. 短命トークンの失効対策（v5で追加）

コンテンツ配信の認証トークンは有効期限2分と短いため、長時間閲覧時にトークン切れが起こりうる。`/p/[uuid]`・`/c/[uuid]`の親ページ側で90秒間隔でトークンを再取得し、iframeの`src`を書き換えることで失効を防ぐ。詳細は設計書4-4節を参照。

---

## 13. 確認ダイアログの基準（v5で追加）

破壊性・復元可能性に応じて確認ダイアログの要否を統一する。公開設定のトグル・メタデータ編集・「外す」操作・バージョンのダウンロードは確認不要（即時反映または無害な操作）。コンテンツ更新・バージョン復元・クリップ削除・コレクション削除は確認ダイアログを必須とする。詳細は設計書9章を参照。

---

## 14. 非機能要件

| 項目 | 内容 |
| --- | --- |
| セキュリティ | クリップ・コレクション単位で公開設定可能。デフォルトはprivate |
| コンテンツ配信 | 別ドメイン（サブドメイン）からiframeサーブ |
| コンテンツ認証 | HMAC-SHA256署名付き短命トークン（有効期限2分） |
| コンテンツサイズ | 1バージョンあたり1MB（1,048,576 bytes）を上限 |
| インフラ | Cloudflare Workers + D1 に統一 |
| バージョン保持数 | 直近10件（`page_versions`） |
| Markdown編集 | 管理画面でのMarkdown編集は将来検討 |
