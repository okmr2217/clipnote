## 1. 役割

`apps/web`は以下をすべて1つのNext.js（App Router）アプリとして実装する。

- 管理画面（`/admin`配下）：クリップ・コレクション・APIキーの管理、アカウント設定
- LP（ランディングページ）
- 公開ページの外枠（`/p/[uuid]` `/c/[uuid]`）：iframeでコンテンツ本体（`content.clipnote.paritto.dev`）を埋め込む親ページ
- better-authによる認証（email/password、パスワードリセット、メール確認）
- MCP用OAuth 2.1認可サーバー（Authorization Server）としての機能（`jwt`・`oauthProvider`プラグイン）。詳細は`docs/design-mcp.md`

## 3. UI／UXデザイン方針

画面の性質によってデザインシステムを使い分ける。`apps/content`・`apps/mcp`は独自のUIを持たないため、本方針は`apps/web`のみに適用される。

| 画面 | 採用方針 | 理由 |
| --- | --- | --- |
| `/admin`配下（管理画面、APIキー管理含む） | **shadcn/ui（挙動レイヤー）+ Tailwind CSS、テーマは3-2節のトークンで完全上書き** | フォーカストラップ・キーボード操作・ARIA属性等のアクセシブルな挙動を実装コストなしで得られるため、コンポーネント（Dialog, Table, DropdownMenu等）はshadcn/uiを採用する。ただし既定の見た目（配色・角丸・フォント）はそのまま使わず、Claude Designで確立したデザイントークンで上書きする |
| LP（ランディングページ） | **カスタム（Tailwind CSSでトンマナ設計）** | ユーザー獲得の入口。「AIが生成したHTML/Markdown、あるいはメモ書きをそのまま保存・公開できる」という価値をビジュアルで訴求する必要があり、shadcnの定型感では差別化しにくい |
| `/p/[uuid]` `/c/[uuid]`のiframe外枠（ヘッダー／フッター） | LPと同じトンマナのカスタム | 公開URLは第三者に共有される二次的なLPとして機能するため |

iframe内部（ユーザー生成コンテンツそのもの、`apps/content`が配信）はデザインシステムの対象外。

### 3-1. デザインの雰囲気

claude.aiに近い、温かみのあるニュートラル基調。テラコッタ〜朱色系のアクセントカラーを1色のみ使用し、余白を広めに取る。ダークモードはMVPでは対応しない（ライトモードのみ）。

### 3-2. デザイントークン

| トークン | 値 | 用途 |
| --- | --- | --- |
| フォント（見出し・本文） | `Plus Jakarta Sans`（サンセリフ） | 見出し・本文とも統一。明朝体・セリフ体は使用しない。見出しは本文より太めのウェイトでコントラストをつける |
| フォント（コード的表示） | `JetBrains Mono` | バイトサイズ表示・URL・APIキー文字列など、等幅が望ましい箇所 |
| アクセントカラー（メイン） | `#C1503A` | 主要なボタン・アクティブ状態・Publicバッジ等 |
| アクセントカラー（濃色バリアント） | `#B5523A` / `#7A3226` | ホバー状態、強調テキスト等 |
| アクセントカラー（淡色バリアント） | `#E4C4B4` | アクセントの背景敷き・淡いハイライト |
| 背景色（クリーム系、明→暗） | `#FBF6F0` → `#F3E9DD` → `#F3E4DA` → `#F1E7DB` → `#E8DCD0` | ページ背景、カード背景、階層による濃淡の使い分け |
| テキストカラー | `#2B2320`（濃）/ `#3D332C` / `#6B5D52` / `#8A7A6D`（淡） | 見出し・本文・補助テキストの階調 |
| 角丸 | 12px（小要素：バッジ・チップ等）〜32px（大きめのカード・ダイアログ）、丸ボタン・アバター等は`999px` | 要素のサイズ・重要度に応じて使い分け |
| 影 | `0 10px 28px -18px rgba(43,35,32,0.18)`（通常のカード等、控えめ）／`0 6px 16px -8px rgba(193,80,58,0.5)`（アクセントカラーを使う要素の強調影） | 強いドロップシャドウは使わない方針を維持 |

## 4. セキュリティ設計（apps/web側の責務）

コンテンツ隔離モデルの全体像・脅威一覧は`docs/design.md`のセキュリティまとめ、コンテンツ配信側の検証処理は`docs/design-content.md`を参照。ここでは`apps/web`が担う部分（トークン生成・公開設定判定・OGP出力・iframe埋め込み）のみを扱う。

### 4-1. コンテンツ隔離とiframe埋め込み

```
[本オリジン] clipnote.paritto.dev/p/[uuid]
  └─ <iframe src="https://content.clipnote.paritto.dev/[uuid]?t=xxx"
             sandbox="allow-scripts allow-popups allow-modals allow-popups-to-escape-sandbox">
```

`/p/[uuid]`・`/c/[uuid]`は`apps/web`のNext.jsページとして実装し、上記の`iframe`タグ（`sandbox`属性含む）を生成する。クリップ本文（HTML）自体の無害化（サニタイズ）は行わない設計であり、`apps/web`側でも本文をそのまま扱ってよい（実行コンテキストの隔離は`apps/content`側のドメイン分離で担保される）。

### 4-2. sandbox属性の内訳

`apps/web`が`iframe`タグに設定する値。

| フラグ | 採用 | 理由 |
| --- | --- | --- |
| `allow-scripts` | ○ | Mermaid等のスクリプト実行に必須 |
| `allow-popups` | ○ | 文書内の外部リンクを新規タブで開く |
| `allow-modals` | ○ | ライブラリ初期化エラー表示等、害は小さい |
| `allow-popups-to-escape-sandbox` | ○ | ポップアップで開いた先に制限を継承させない |
| `allow-same-origin` | ✕（付けない） | Cookie/Storage窃取を防ぐセキュリティの核 |
| `allow-forms` | ✕ | 文書中心の用途では不要 |
| `allow-top-navigation`系 | ✕ | フィッシング対策として付けない |

### 4-3. Cookieスコープ

親ドメイン`paritto.dev`を共有するため、iframe隔離による多層防御の効果を実質的に確保するには、**better-authのセッションCookieの`Domain`属性を`clipnote.paritto.dev`というホスト単体にスコープする**（`Domain`属性を省略し、親ドメイン全体に広げない）ことを実装時に必ず確認する。`apps/mcp`はセッションCookieを一切使わない設計のため、この注意点の対象外（`docs/design-mcp.md`参照）。

### 4-4. トークン生成・自動更新（apps/web側フロー）

別ドメイン（`apps/content`）にはセッションCookieが届かないため、`apps/web`がセッションCookieでアクセス権を確認したうえで、署名付き短命トークン（**有効期限：2分**）を発行する。

```
① 本オリジン /p/[uuid] または /c/[uuid] にアクセス
      ↓ セッションCookieで認証確認 + クリップ／コレクションのアクセス権確認
② サーバーサイドでHMAC-SHA256署名付き短命トークンを生成
      ↓ CONTENT_TOKEN_SECRET（apps/web・apps/content共通の環境変数）で署名
③ iframe src="https://content.clipnote.paritto.dev/[uuid]?t=xxx"
```

トークンの構造：

```
payload = "{userId}:{uuid}:{exp}"
sig     = HMAC-SHA256(payload, CONTENT_TOKEN_SECRET)
token   = base64url("{payload}:{sig}")
```

生成・検証ロジックは`packages/content-token`として`apps/web`（生成）・`apps/content`（検証）の両方から参照する共有パッケージにする。検証側の処理フローは`docs/design-content.md`参照。

#### トークンの自動更新

- `/p/[uuid]`・`/c/[uuid]`の親ページ側で、**90秒間隔**で新しいトークンをサーバーから取得し、iframeの`src`属性を新トークンで書き換える（初回表示から2分経過する前に更新する設計）
- 更新はiframeの再読み込みを伴わない形（`src`のクエリパラメータのみ差し替え）を基本とするが、ブラウザ実装によっては同一パス+クエリ変更でも再読み込みが発生しうるため、実装時に挙動を確認する
- トークン取得APIが失敗した場合（セッション切れ等）は、静かに更新を諦め、次回の定期実行を待つ（エラー表示でユーザー体験を損なわない）

### 4-5. 公開設定の扱い（クリップ／コレクション）

トークン発行可否の判定は`apps/web`側（セッションCookie検証＋DB参照）で行う。

| ケース | 挙動 |
| --- | --- |
| privateクリップ（認証済み本人がアクセス） | 通常通りトークン発行 |
| publicクリップ | 認証なしでもトークンを発行 |
| privateコレクション | 認証済み本人のみ`/c/[uuid]`にアクセス可。全所属クリップを一覧表示 |
| publicコレクション（本人以外／未認証がアクセス） | 認証不要で`/c/[uuid]`にアクセス可。**所属クリップのうち`private`のものは一覧から除外** |
| publicコレクション（本人が認証済みでアクセス） | 全所属クリップを一覧表示 |

### 4-6. OGP・シェア時のメタデータ

`/p/[uuid]` `/c/[uuid]`は`apps/web`のNext.jsページのため、OGPメタタグも`apps/web`側で出力する。

| 対象 | 挙動 |
| --- | --- |
| publicなクリップ／コレクション | タイトル・説明文を`og:title` / `og:description`として出力。`og:image`は当面固定のブランド画像（Clipnoteのロゴ等）を使用 |
| privateなクリップ／コレクション | OGPタグを一般的な固定文言のみにし、タイトルや説明などクリップ固有の情報は出力しない |

将来、スクリーンショット生成機能（`docs/design.md`将来検討）が実装され次第、`og:image`を動的なプレビュー画像に差し替える段階的対応とする。

### 4-7. MCP認証との関係（概要）

`apps/mcp`はセッションCookie・HMACトークンいずれとも異なる認証（APIキー方式・OAuth 2.1方式）を用いる。`apps/web`はAPIキーの発行画面（8章）とOAuth 2.1の認可サーバー機能の両方をホストするが、詳細な認証フロー・データモデルは`docs/design-mcp.md`にまとめる。

### 4-8. サインアップの悪用対策（レート制限）

better-authの`rateLimit`設定（`src/lib/auth.ts`）を有効化し、捨てアドレスでの大量サインアップ・APIキー発行の踏み台化を抑止する。

- **既定ルール**：better-authの一般API向け既定（10秒10回）をそのまま使用
- **`/sign-up/email`個別ルール**：同一キー（IPアドレス単位）から1時間5回まで
- **storage**：`"database"`（`rateLimits`テーブル、9章）。Cloudflare Workersはリクエストごとにisolateが再利用されるとは限らず、既定の`"memory"`ではカウントが揮発してしまうため、D1に永続化する
- CAPTCHA（Cloudflare Turnstile等）の導入は将来検討。まずはレート制限のみで初期の悪用を抑止する

## 5. コンテンツバリデーション

セキュリティ目的ではなく、UX・データ整合性・インフラコスト管理を目的とする。管理画面（`apps/web`）経由・MCP（`apps/mcp`）経由（`upload_page`/`update_page`）いずれも共通のバリデーション関数（`packages/db`または共有バリデーション関数）を通す。

### 5-1. 形式（HTML/Markdown/プレーンテキスト）の妥当性

| チェック内容 | 扱い |
| --- | --- |
| 完全なHTML文書構造（`<html>`/`<body>`必須） | 要求しない（AI生成の断片的なマークアップを許容する） |
| タグの閉じ忘れなどの構文エラー | チェックしない（ブラウザの寛容なパースに委ねる） |
| Markdownとしての妥当性 | チェックしない |
| 空文字列でないか | チェックする |
| 有効なUTF-8か | チェックする |
| 形式の決定（管理画面のみ） | ユーザーによる手動選択は行わない。ファイル読み込み時は拡張子（`.html`/`.htm`→HTML、`.md`/`.markdown`→Markdown、`.txt`→プレーンテキスト、**v9で変更**）を優先する。貼り付け・未対応拡張子の場合は、①本文にHTMLタグらしき記述が含まれるか→HTML、②見出し・リスト・引用・コードブロック・表・リンク・強調・区切り線などMarkdownらしい記法が含まれるか→Markdown、③どちらでもなければプレーンテキスト、の順で大まかに判定する（**v9でプレーンテキストの判定を追加**。厳密なCommonMark判定はしない）。MCP経由は`content_type`を呼び出し側が明示するため自動判定は行わない（`docs/design-mcp.md`参照） |

### 5-2. データサイズの上限

| 項目 | 値 | 備考 |
| --- | --- | --- |
| 1クリップ（1バージョン）あたりの本文サイズ上限 | **1MB（1,048,576 bytes）** | Cloudflare D1の行サイズ上限2MBに対し安全マージンを確保 |
| 判定基準 | バイト数（UTF-8エンコード後） | 文字数ではなくバイト数で判定 |
| バージョン10件保持時の1クリップあたり最大ストレージ | 約10MB | 9章の`page_versions`参照 |

- クライアント側（管理画面）は本文確定時に上限バイト数を判定し、超過している場合はエラーメッセージで差し戻す（確定表示のカードには常時のバイト数表示は行わない。5-4節・6-2節参照）
- サーバー側でも必ず再チェックする（`apps/web`・`apps/mcp`共通）

### 5-3. ファイル読み込み時の追加チェック（管理画面のみ）

- 拡張子が`.html` `.htm` `.md` `.markdown` `.txt`以外の場合は警告（`.txt`は**v9**からプレーンテキストとして扱う）
- `File.size`を用いて、実際にテキストとして読み込む前にサイズ上限を事前チェックする
- 文字化け検知：U+FFFD等の異常値が一定割合以上含まれる場合、UTF-8確認の警告を表示（保存はブロックしない）

### 5-4. タイトルの自動取得（新規クリップ登録のみ）

本文確定時（貼り付け・ファイル読み込み共通）に、タイトル欄が未入力（ユーザーが一度も編集していない）であれば自動反映する。一度でも手動編集した場合は上書きしない。取得できたタイトル候補は確定表示カード内にも表示する（6-2節参照。バイト数の代わりにこちらを表示する）。コンテンツ更新ダイアログはタイトルを変更しない仕様（6-4節）のため対象外。

優先順位は「本文から抽出したタイトル → ファイル名（拡張子除去） → 反映しない（空のまま手動入力）」。AI生成コンテンツは断片的なファイル名より本文中のタイトルの方が説明的なため、本文からの抽出を優先する。

| 形式 | 抽出方法 |
| --- | --- |
| HTML | `<title>`タグのテキスト。無ければ最初の`<h1>`のテキスト |
| Markdown | 本文先頭の`# 見出し`（H1）のみ。見出し以外の先頭行（表・コードブロックの断片等）はタイトル扱いにしない（誤検知防止のためフォールバックしない） |
| プレーンテキスト（**v9で追加**） | 先頭の空行を除いた最初の行をそのままタイトル候補とする。見出し構文を持たない形式のため、空でなければ無条件に採用する（会議メモ等では一行目がタイトルのように書かれることが多いため） |

抽出したタイトルが120文字を超える場合は切り詰める。

## 6. 画面設計：クリップ管理

### 6-1. クリップ一覧（`/admin`）

**デスクトップ（`md`以上）：テーブル形式**

| 表示列 | 内容 |
| --- | --- |
| 形式バッジ | `HTML` / `MD` / `TXT`（**v9で追加**）。**固定済みクリップはピンアイコンを併記（v10で追加）** |
| タイトル | クリックでプレビューを新規タブで開く。**アーカイブ済みクリップは「アーカイブ済み」バッジを併記し、行全体を淡色表示にする（v10で追加）** |
| 公開設定 | バッジ。クリックでその場でトグル（即時反映） |
| 所属コレクション | チップ表示（複数可） |
| 更新日時 | ソート軸（**v10で「固定→更新日時降順」の2段ソートに変更。固定クリップを常に先頭にまとめ、固定クリップ同士・非固定クリップ同士はそれぞれ更新日時降順**） |
| 公開URLコピー | Publicなクリップの行に常時表示 |
| 操作 | プレビュー／メタデータ編集／コンテンツ更新／更新履歴／**固定・固定解除／アーカイブ・アーカイブ解除（v10で追加）**／削除＝ゴミ箱へ移動（オーバーフローメニュー。**v12でゴミ箱方式に変更**。確認ダイアログなし、Undoトースト表示） |

**固定・アーカイブのフィルタ（v10で追加）**：一覧上部のフィルタ列に「状態」セレクトを追加し、「アクティブのみ」（既定、アーカイブ済みを除外）／「アーカイブ済みのみ」／「すべて」を切り替えられる。他のフィルタ（形式・公開設定・コレクション・検索）と同様にクライアント側でのフィルタリングとする。

**モバイル（`md`未満）：カード形式**

### 6-2. 新規クリップ登録：ダイアログ

本文入力は「入力待ち」→「確定表示」の2段階UIとする。入力待ち状態では「テキストを貼り付け」と「ファイルをアップロード」を別ブロックに分けて表示し、それぞれに説明文を添える。貼り付け欄は他の入力欄（タイトル等）と同じ見た目・高さの1行テキストフィールドとし、複数行貼り付け時は内部スクロールで保持する（値そのものは改行を含む全文を保持し、表示上だけ縮めている）。確定後は形式・ファイル名（または「貼り付けされたHTML/マークダウン/プレーンテキスト」）・取得したタイトル候補（あれば）をカード状に表示する。形式のユーザーによる手動選択は行わない（5-1節参照）。バイト数は確定表示カードには常時表示しない（5-2節参照。上限超過時は確定時のエラーメッセージで示す）。

```
┌─────────────────────────────────────┐  入力待ち
│ 新規クリップ                           │
├─────────────────────────────────────┤
│ テキストを貼り付け                       │

│ 会話ログやメモ書きなどのプレーンテキストを │
│ そのまま貼り付けてください。形式は自動で   │
│ 判定されます。                          │

│ └───────────────────────────────┘  │
│                              [確定]   │  ← 本文入力中のみ表示
│                 ── または ──          │
│ ┌ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐  │
│ │ ファイルをアップロード [ファイルを選択] │  │
│ │ ドラッグ&ドロップ、または選択してくださ │  │
│ │ い（.html/.md/.txt等）。ブラウザ内で   │  │
│ │ のみ読み込まれ、送信されません          │  │

│                                       │

┌─────────────────────────────────┐  確定後
│ 新規クリップ                       │
├─────────────────────────────────┤
│ ┌───────────────────────────┐   │
│ │ [HTML] report.html            │   │
│ │ Q3 Sales Report    [変更する] │   │  ← 取得したタイトル候補
│ └───────────────────────────┘   │
│                                   │

貼り付けは、テキストエリアへのペースト直後に自動で確定表示へ切り替える。ファイルはサーバーへアップロードしない。`File.text()`でクライアント側のみでファイル内容を読み取り、本文へ反映し、タイトル候補（5-4節参照）をタイトル初期値に反映する。サーバーへ送信するのは、貼り付け・ファイルいずれの経路でも本文の文字列＋メタデータのみ。「変更する」で入力待ち状態へ戻り、本文を空にして再入力できる。

### 6-4. コンテンツ更新：破壊的操作として分離

6-2節と同じ入力UIを再利用しつつ、次の点で新規登録と区別する。

- ダイアログタイトルを「クリップ本文の差し替え」のように明示
- 警告文：「既存の本文を上書きします。この操作は更新履歴として記録され、後から復元・ダウンロードできます」
- 現在の本文と新しい本文のサイズ差分を表示
- タイトル・公開設定・所属コレクションは変更されない旨を明記
- 実行ボタンは警告色（`destructive`バリアント）

内部処理：更新前の本文を`page_versions`へ退避してから`pages.content`を更新する（9-2節参照）。この処理はMCP経由の`update_page`（`docs/design-mcp.md`参照）とも共有ロジックとして実装する。

### 6-5. 更新履歴・バージョンの復元／ダウンロード

`/admin/pages/[uuid]`から辿れる。差分（diff）表示は行わず、全文プレビューでの確認ベースとする。

**現在のバージョンにも過去のバージョンにも「ダウンロード」を提供する。復元は過去のバージョンにのみ提供する。**

```
┌─────────────────────────────────┐
│ 更新履歴                          │
├─────────────────────────────────┤
│ ● 現在のバージョン (v5)             │
│   2026-08-04 10:20    [ダウンロード] │
│                                   │
│ ○ v4 [MCP（APIキー）] 2026-08-03 18:02  [プレビュー][ダウンロード][復元] │
│ ○ v3 [管理画面]      2026-08-01 09:15  [プレビュー][ダウンロード][復元] │
│ ○ v2 [MCP（OAuth）]  2026-07-30 14:40  [プレビュー][ダウンロード][復元] │
│ ○ v1 [管理画面]      2026-07-28 11:00  [プレビュー][ダウンロード][復元] │
│                                   │
│ （直近10件のみ保持）                 │
└─────────────────────────────────┘
```

- 「プレビュー」：そのバージョンの内容を別ドメインiframeで簡易レンダリング表示
- 「ダウンロード」：クライアント側でBlob生成しファイル保存。サーバー通信不要。ファイル名は`{タイトル}_v{番号}.{html|md|txt}`形式（現在のバージョンは`{タイトル}.{html|md|txt}`。`plaintext`は`.txt`、**v9で追加**）
- 「復元」：実行すると、復元前の現在の内容も新しいバージョンとして履歴に退避してから上書きする（＝復元自体も1回の更新として記録される）
- 各バージョンの実行元（`page_versions.source`）をバッジ表示する：「管理画面」／「MCP（APIキー）」／「MCP（OAuth）」（**v13で追加**、9章参照）
- ダウンロードは無害な操作のため確認ダイアログ不要（7-1節参照）

### 6-6. クリップ一覧＋プレビュー（`/admin/clips`、v11でβ追加）

既存の`/admin`（6-1〜6-5節のテーブル/カード一覧）と並行稼働する、デスクトップ専用の2カラムレイアウト。左を「探す」ための軽量な索引、右を「読む・操作する」ためのプレビューパネルとして役割を分離する。モバイル（`md`未満）は非対応で、既存の`/admin`一覧へ誘導する文言のみを表示する。双方の画面はヘッダーの案内リンクで相互に行き来できる。

```
┌──────────────┬──────────────────────────────────────┐
│ クリップ 12件 [+]│ 週次AI議事録まとめ    [固定中][コンテンツ更新]… │
│ [検索]           │ [MD] [公開] コレクションチップ [🔗] [更新履歴]  │
│ [状態][形式][公開]│──────────────────────────────────────│
│──────────────│                                        │
│ 固定             │        ContentFrame（iframeプレビュー）   │
│ 📌 週次AI議事録… ●│                                        │
│──────────────│                                        │
│ すべてのクリップ  │                                        │
│ プロジェクトA…   │                                        │
│ 先週の振り返り…  │                                        │
└──────────────┴──────────────────────────────────────┘
```

**左ペイン（一覧）**：

- 検索（タイトル部分一致）・状態フィルタ（アクティブのみ/アーカイブ済みのみ/すべて、既定はアクティブのみ）・形式フィルタ・公開設定フィルタを備える
- 固定クリップは「固定」セクション、それ以外は「すべてのクリップ」セクションに分けて表示し、6-1節のソート（固定→更新日時降順）をそのまま視覚化する
- 行に表示する情報は、形式バッジ・固定アイコン・タイトル・公開設定（色ドットのみ、クリック操作はしない）・更新日時（短縮表記）・アーカイブ済みラベルに絞る。所属コレクション・公開URLコピー・各種操作（メタデータ編集/コンテンツ更新/削除等）は行には置かず、右ペインのヘッダーに集約する（情報密度を下げ、340px幅の一覧でもスキャンしやすくする）
- 行をクリックすると右ペインにそのクリップをプレビューする（ページ遷移なし）

**右ペイン（プレビュー）**：

- ヘッダーにタイトル・形式バッジ・公開設定（クリックでトグル、実際の切替操作はここでのみ行う）・所属コレクションのチップ・公開URLコピー・更新日時・更新履歴へのリンクを表示する
- 固定/固定解除・コンテンツ更新・メタデータ編集・アーカイブ/アーカイブ解除・削除のボタンを備える。ダイアログ・確認基準（7章）は6章と共通のコンポーネントをそのまま再利用する
- 本文プレビューは`/p/[uuid]`と同じ`ContentFrame`（4-4節のトークン方式、90秒毎の自動更新）をそのまま再利用する。一覧で別の行を選択すると、選択時に`POST /api/content-token`でそのクリップ用のトークンを取得してから`ContentFrame`を差し替える（`uuid`が変わるとコンポーネント内部で正しく再マウントされる設計のため、追加のリセット処理は不要）
- 初回表示・未選択時は一覧の先頭（＝固定優先ソートの先頭、通常はアクティブな最新のクリップ）を自動選択し、空のプレビューを見せない
- コンテンツ更新後は同じクリップのプレビューを再読み込みする。削除されたクリップが選択中だった場合は選択を解除する

**将来検討**：行内でのホバー操作（固定・アーカイブのクイックトグル）、一覧・プレビューを分けるスプリッターのリサイズ対応、モバイル対応。既存`/admin`との統合（どちらかへの一本化）は、β運用してから判断する。

### 6-7. ゴミ箱（`/admin/trash`、v12で追加）

削除（＝ゴミ箱へ移動）したクリップを30日間保持する画面。詳細仕様は`docs/design-trash.md`3章を参照。`/admin`のナビゲーションから遷移する。デスクトップ・モバイルの両方に対応する（6-6節のβレイアウトとは異なり、モバイル非対応にはしない）。

- 表示列：形式バッジ・タイトル・削除日時・自動削除までの残り日数
- 操作：「復元」（即時反映、確認ダイアログ不要）・「完全に削除」（確認ダイアログ必須、唯一の不可逆操作）
- 30日経過後は日次バッチ（Cloudflare Cron Trigger）で自動的に物理削除される

## 7. 確認ダイアログの一貫した基準

破壊性・復元可能性に応じて、確認ダイアログの要否を統一する。すべて`apps/web`（`/admin`配下）の画面に適用される基準。

### 7-1. 基準表

| 操作 | 確認ダイアログ | 理由 |
| --- | --- | --- |
| 公開設定のトグル | 不要（即時反映） | 何度でも戻せる |
| メタデータ編集の保存 | 不要 | 低リスク |
| コレクションから「外す」 | 不要 | クリップ自体は残る |
| バージョンのダウンロード | 不要 | 状態変更を伴わない無害な操作 |
| クリップの固定/固定解除（**v10で追加**） | 不要（即時反映） | 何度でも戻せる |
| クリップのアーカイブ/アーカイブ解除（**v10で追加**） | 不要（即時反映） | クリップ自体・更新履歴・所属コレクションは残り、いつでも解除できる |
| クリップ削除＝ゴミ箱へ移動（**v12でゴミ箱方式に変更**） | 不要（Undoトーストで取り消し可能） | 30日間はゴミ箱から復元できるため可逆操作になった |
| ゴミ箱からの復元（**v12で追加**） | 不要（即時反映） | 何度でもやり直せる |
| コンテンツ更新（本文差し替え） | **必要**（警告文＋サイズ差分表示） | 復元可能だが心理的インパクトが大きい |
| バージョンの復元 | **必要**（「vNの内容で上書きします」の確認） | 現在の内容を意図せず失うと感じやすい |
| ゴミ箱からの完全削除（**v12で追加**） | **必要**（「元に戻せません。更新履歴ごと完全に削除されます」を明記） | 完全に元に戻せない唯一の不可逆操作（バージョン履歴ごと消える） |
| コレクション削除 | **必要**（「クリップ自体は消えません」を明記） | 誤解されやすいため文言が重要 |
| 公開コレクション内の非公開クリップを一括公開（**v14で追加**） | **必要**（対象件数と「第三者でも閲覧できるようになる」旨を明記） | 複数クリップの公開設定が一括で変わり、影響範囲が大きい |
| APIキーの失効 | **必要**（「連携が利用できなくなる」旨を明記） | 再発行が必要になり元に戻せない |
| 連携中のアプリの失効（`docs/design-mcp.md`参照） | **必要**（「再度認可が必要になる」旨を明記） | 再認可が必要になり元に戻せない |

## 8. 画面設計：コレクション管理

### 8-1. コレクション一覧（`/admin/collections`）

クリップ一覧（6-1節）と対称的な構成にするが、以下の点はクリップと異なる。

**デスクトップ（`md`以上）：テーブル形式**

| 表示列 | 内容 |
| --- | --- |
| コレクション名 | クリックで**詳細画面へ遷移**（同タブ）。クリップ一覧の「クリック→プレビュー別タブ」とは意図的に非対称。コレクション単体のプレビューという概念がなく、詳細画面に入るのが自然な動線のため |
| 説明 | 1行省略表示。**未入力の場合は「説明なし」を淡色プレースホルダーで表示**（空欄のままにしない） |
| 公開設定 | バッジ、クリックでトグル |
| 所属クリップ数 | バッジ表示（例：「3件」）。**0件のコレクションも特別な視覚処理はせず通常表示** |
| 更新日時 | ソート軸 |
| 公開URLコピー | Publicなコレクションに常時表示 |

**オーバーフローメニューの項目**：「編集」「削除」の**2項目のみ**。クリップのような「コンテンツ更新」「更新履歴」に相当する概念がコレクションにはないため。

**モバイル（`md`未満）：カード形式**（クリップ一覧のカードと同様の構成）

**新規作成フロー**：「＋ 新規コレクション」から名前・説明・公開設定のみの軽量ダイアログ。**作成完了後は自動的に詳細画面（8-2節）へ遷移し、その画面上で「クリップを追加」ダイアログ（8-4節）を開いた状態にする。** 作成ダイアログ自体に入力項目を追加するのではなく、次のアクションへの導線を画面遷移で担保する設計とする。

### 8-2. コレクション詳細（`/admin/collections/[uuid]`）

```
┌─────────────────────────────────────┐
│ コレクション: 議事録まとめ                │
│ 説明: 週次AI議事録をまとめたもの            │
│ 公開設定: ● Public   [情報を編集]          │
│ [🔗 公開URLをコピー]  [公開ページで見る ↗]  │
├─────────────────────────────────────┤
│                          [+ クリップを追加] │
│ ⠿  [HTML] 今日のAI議事録まとめ      [外す] │
│ ⠿  [MD]   先週の振り返りメモ        [外す] │
│ ⠿  [HTML] プロジェクトA議事録       [外す] │
└─────────────────────────────────────┘
```

- 公開設定が`public`の場合、クリップ一覧と同様に「公開URLコピー」ボタンを表示
- 「公開ページで見る」リンク（`/c/[uuid]`を新規タブで開く）を追加。所有者本人は非公開クリップも含め全件見える（4-5節）ため実際の来訪者視点そのものではないが、レイアウト確認用として有用

クリップが0件の場合は空状態表示（「まだクリップがありません。［＋ クリップを追加］」）とする。クリップ件数が多い場合でもページネーションは実装しない（通常のスクロールで対応。MVP規模での運用を想定）。

**非公開クリップの一括公開（v14で追加）**：公開コレクションに非公開クリップが含まれる場合の既存の警告表示（4-5節・8-1節の「所属クリップのうち`private`のものは一覧から除外」の裏返し）に、「非公開クリップをすべて公開にする」操作を追加する。

- 警告文の直下にリンクボタンとして配置する（常時表示のボタンにはしない。非公開クリップが0件になれば警告ごと消える）
- クリックすると警告ダイアログを表示し、対象件数と「公開URLから第三者でも閲覧できるようになる」旨を明記する（7章の基準表参照）
- 確認後、当該コレクションに所属する非公開クリップのみを一括で`public`に更新する。コレクション自体の公開設定・他コレクションへの影響はない
- クリップ単位の個別トグル（6-1節・6-3節）と同じ即時反映のPATCH相当の扱いだが、複数件を一度に変更する操作のため確認ダイアログを必須とする点が個別トグルと異なる

### 8-3. 並び替えUX

デスクトップとモバイルで実装方式を分ける。

| 環境 | 方式 | 理由 |
| --- | --- | --- |
| デスクトップ（`md`以上） | ドラッグ&ドロップ（ドラッグハンドル`⠿`付き） | マウス操作なら誤操作が起きにくく直感的 |
| モバイル（`md`未満） | 並び替えモード＋上下移動ボタン | タッチドラッグはスクロールと衝突しやすい。明示的な「並び替えモード」に入り`↑` `↓`ボタンで1件ずつ動かす |

**デスクトップの挙動詳細**：
- ドラッグ中、ドロップ予定位置に**プレースホルダー（挿入位置を示す線）**を表示する
- ドロップ確定時に、影響を受けた行の`sort_order`をまとめて1回のAPIコールとして送信する（書き込み回数を抑制）

**モバイルの挙動詳細**：

```
モバイル（並び替えモード）
┌───────────────────────────────┐
│ 並び替え中            [完了]     │
├───────────────────────────────┤
│ [HTML] 今日のAI議事録まとめ  ↑ ↓  │
│ [MD]   先週の振り返りメモ    ↑ ↓  │
└───────────────────────────────┘
```

- 並び替えモード中の`↑` `↓`ボタンによる移動は、**サーバーへは送信せずローカル状態のみ即時反映**する
- 「完了」ボタンを押した時点で、影響を受けた行の`sort_order`をまとめて1回のAPIコールとして送信する
- **「完了」を押さずに画面を離れた場合（戻る操作・別画面への遷移など）は、変更を破棄し元の順序に戻す**（サーバーへの送信は一切行わない）。実装上は、並び替えモード中はローカルstate（メモリ上のコピー）でのみ順序を保持し、実際のリスト表示に反映しているデータとは分離しておく
- 実装ライブラリは`dnd-kit`を推奨（キーボード操作にも対応しアクセシビリティ面で有利）
- 並び替えモード中は、プレビュー等の通常操作を無効化する

### 8-4. クリップの追加

```
┌─────────────────────────────────┐
│ クリップを追加                     │
├─────────────────────────────────┤
│ 検索: [______________]             │
│                                   │
│ ☑ [HTML] 今日のAI議事録まとめ         │
│ ☐ [MD]   先週の振り返りメモ           │
│ ☐ [HTML] プロジェクトA議事録（追加済み）│
│                                   │
│              [キャンセル] [追加]     │
└─────────────────────────────────┘
```

**仕様**：
- 自分の全クリップを対象に、**更新日時の新しい順**で一覧表示（クリップ一覧画面のデフォルトソートと統一）
- 検索は**タイトルの部分一致**
- 各行に**形式バッジ（HTML/MD/TXT）**を表示し、選択時の判断材料にする
- 既に所属しているクリップはチェック済みで表示し、チェックの付け外しで追加／除外の両方を1つのUIで扱う
- **アーカイブ済みクリップの扱い（v10で追加）**：新規に選択肢として追加することはできないよう一覧から除外する（クリップ一覧のデフォルトフィルタと同様の考え方）。ただし、**既にこのコレクションに所属しているクリップがアーカイブされた場合は一覧から消さず**、「アーカイブ済み」バッジを付けてチェック済みのまま表示する（外すかどうかはユーザーの明示的な操作に委ねる）
- **新規追加時の並び順（v11で追加）**：コレクションはクリップを都度追加していくタイムライン的な使い方を想定しているため、新規に追加したクリップは一覧の**先頭**に並べる（末尾追加ではない）。既存クリップの`sort_order`は変更しない。複数件を同時に追加した場合は、選択順を保った状態でまとめて先頭に挿入する。この並び順はデフォルトの初期配置であり、追加後は8-3節の並び替えUXで自由に変更できる

### 8-5. 「外す」と「削除」の区別

| 操作 | 意味 | 実装箇所 | 確認ダイアログ |
| --- | --- | --- | --- |
| 「外す」 | `collection_pages`の関連付けのみ削除。クリップ自体は残る | コレクション詳細画面 | 不要（即時実行） |
| 「削除」 | クリップ本体（`pages`行）を削除。全コレクションから自動的に外れる | クリップ一覧・クリップ詳細画面 | 必要 |

┌─────────────────────────────┐
│ コレクション情報を編集           │
├─────────────────────────────┤
│ 名前: [______________]        │
│ 説明: [______________]        │
│ 公開設定: ○ Private ● Public  │
│                               │
│           [キャンセル] [保存]  │

```

## 9. データモデル（apps/webが所有するテーブル）

`docs/design.md`のデータモデル索引も参照。DBスキーマ（`packages/db`）自体は全アプリ共有だが、以下は`apps/web`が発行・更新の主体となるテーブル。

### `users`テーブル（better-auth管理）

better-authが管理する標準スキーマを利用（email/password認証）。

### `rate_limits`テーブル（better-auth管理、4-8節で追加）

better-authの`rateLimit`プラグイン設定（`storage: "database"`）が内部的に読み書きする。`key`（IPアドレス等の識別子＋ルール）・`count`（ウィンドウ内リクエスト数）・`last_request`（最終リクエスト時刻、ミリ秒）のみを持ち、アプリケーションコードから直接参照することはない。

### `pages`テーブル

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| user_id | uuid | FK → users |
| title | text | クリップタイトル |
| content | text | コンテンツ本体（現在のバージョン） |
| content_type | enum | `html` / `markdown` / `plaintext`（**v9で追加**） |
| visibility | enum | `private` / `public` |
| pinned | boolean | 固定フラグ。既定`false`（**v10で追加**）。一覧のソート優先度に使う（6-1節） |
| archived_at | timestamp | nullable。非nullならアーカイブ済み（**v10で追加**）。削除とは異なりクリップ本体は保持したまま一覧のデフォルト表示から除外する |
| deleted_at | timestamp | nullable。非nullならゴミ箱内（**v12で追加**）。物理削除（30日後の自動パージ、または「完全に削除」操作）まで`page_versions`・`collection_pages`は変更しない。詳細は`docs/design-trash.md` |
| created_at | timestamp | |
| updated_at | timestamp | |

> `content`のサイズ上限：1MB（1,048,576 bytes、UTF-8）。アプリケーション側でバリデーション（5-2節）。`apps/web`・`apps/mcp`共通。

### `collections`テーブル

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| user_id | uuid | FK → users |
| name | text | コレクション名 |
| description | text | コレクションの説明（任意） |
| visibility | enum | `private` / `public` |
| created_at | timestamp | |
| updated_at | timestamp | |

### `collection_pages`テーブル（中間テーブル）

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| collection_id | uuid | FK → collections（`ON DELETE CASCADE`） |
| page_id | uuid | FK → pages（`ON DELETE CASCADE`） |
| sort_order | int | コレクション内の表示順（DnD／上下ボタンで操作） |
| created_at | timestamp | |

### `page_versions`テーブル

コンテンツ更新時に、更新前の内容を退避するためのバージョン履歴テーブル。ダウンロード機能・復元機能の両方で参照される。`apps/web`経由・`apps/mcp`経由（`update_page`）いずれの更新でも同じロジックで退避する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| page_id | uuid | FK → pages（`ON DELETE CASCADE`） |
| content | text | その時点でのコンテンツ本体 |
| content_type | enum | `html` / `markdown` / `plaintext`（**v9で追加**） |
| version_number | int | 1から始まる連番（page_id内で一意） |
| source | enum | `web` / `api_key` / `oauth`。このスナップショットを退避させた更新操作の実行元（**v13で追加**） |
| created_at | timestamp | このバージョンが作られた日時 |

**運用方針**：

- `pages.content`は常に「現在のバージョン」を保持する
- 更新の流れ：①更新前の`pages.content`を`page_versions`へ退避（新しい`version_number`でINSERT）→ ②`pages.content`を新しい内容でUPDATE
- 復元の流れ：①復元前の現在の内容を`page_versions`へ退避 → ②選択したバージョンの内容で`pages.content`をUPDATE（＝復元も1回の更新として履歴に残る）
- ダウンロードの流れ：現在のバージョンは`pages.content`、過去のバージョンは該当行の`content`を、いずれもクライアント側でBlob化してファイル保存（サーバー側の追加処理は不要）
- 保持件数：直近10件を上限とし、超過分は古いものから削除する
- タイトル等の軽量なメタデータはバージョン管理の対象外（本文のみ）
- **`source`（v13で追加）**：管理画面からの更新・復元は`web`、MCP経由の`update_page`はAPIキー認証なら`api_key`、OAuth認証なら`oauth`を記録する。更新履歴画面（6-5節）に来歴として表示する。この列の追加以前に存在した行は実際の実行元が不明なため、マイグレーションで一律`web`を補完している（後方互換のための近似値であり、正確な来歴ではない）

### `api_keys`テーブル

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| user_id | uuid | FK → users（`ON DELETE CASCADE`） |
| name | text | ユーザーが付けた名前（例:「Claude Desktop用」）、必須 |
| key_hash | text | APIキーのハッシュ値（bcrypt等）。生キーは保存しない |
| key_prefix | text | 一覧でのマスク表示用（先頭数文字＋末尾4文字を保持、または生成時に別途保持） |
| created_at | timestamp | |
| last_used_at | timestamp | nullable。MCPリクエスト認証成功のたびに更新 |

**運用方針**：
- キーのフォーマットは`cn_live_{ランダム文字列32文字程度}`（暗号学的に安全な乱数で生成）
- 発行時のみ生のキー全文をレスポンスで返す。以降はハッシュ照合のみで検証し、平文は保持しない
- スコープ分け（read/write）は設けず、全キー同一権限（将来検討、`docs/design.md`参照）

APIキーのハッシュ照合ロジックは、`apps/web`（発行）と`apps/mcp`（検証）の両方から参照するため、`packages/auth`として共有パッケージ化している。

## 11. 画面設計：アカウント設定

better-authのコア機能（`emailAndPassword`・`emailVerification`）のみで実現し、新規プラグインもDBスキーマの変更も不要。既存の`users.email_verified`列・`verifications`テーブルをそのまま使う。

### 11-1. パスワードリセット（`/forgot-password`・`/reset-password`）

- `/forgot-password`：メールアドレス1項目のみのフォーム。送信後は、メールアドレスが実在するか否かに関わらず**同一の成功メッセージ**を表示する（列挙対策）。実際の送信要否の判定・トークン発行はbetter-auth側（`emailAndPassword.sendResetPassword`コールバック）が行う
- `/reset-password?token=...`：メール本文のリンクからアクセス。新パスワード＋確認の2項目。`token`が無い場合はフォームを表示せず、リンク切れの案内を表示する
- 成功後は`/login?reset=1`へ遷移し、ログイン画面に成功メッセージを表示する

### 11-2. メール確認（サインアップ時、任意）

- サインアップ成功時にbetter-authが確認メールを自動送信する（`sendOnSignUp: true`）。サインアップ画面自体の変更はない
- **未確認でも機能制限は一切行わない**（クリップ作成・閲覧・APIキー発行等すべて利用可）。`/admin`配下のレイアウトに、`emailVerified === false`のときだけ非ブロッキングのバナー（`EmailVerificationBanner`）を表示し、再送信ボタンを設ける
- 確認リンクを踏むとbetter-authのcatch-allルート（`/api/auth/verify-email`）がトークンを検証し、`callbackURL`（`/admin`）へリダイレクトする。専用ページは不要

### 11-3. パスワード変更・アカウント設定画面（`/admin/settings`）

- ナビゲーションに「アカウント設定」を追加（`AdminHeader`の`NAV_ITEMS`、APIキー管理の右隣）
- 画面には名前・メールアドレス・メール確認状態（バッジ表示）を表示し、「パスワードを変更」ボタンから`ChangePasswordDialog`を開く（0章・6章・8章の「新規作成・編集はダイアログ」方針に準拠。ページ自体は編集フォームではなく情報表示＋エントリポイントのため新設して問題ない）
- ダイアログの項目は現在のパスワード・新パスワード・確認の3項目。変更成功時は**他端末のセッションを無効化**する（`revokeOtherSessions: true`）。パスワード漏洩時などに古いセッションが残り続けるリスクを避けるため

### 11-4. メール送信基盤

- Cloudflare Email Service（`send_email`バインディング、`apps/web/wrangler.jsonc`）を使用。送信元は`noreply@clipnote.paritto.dev`
- 送信元ドメイン（`paritto.dev`）のCloudflare Email Sending有効化はCloudflareアカウントに対する手動作業（`wrangler email sending enable`等）であり、本書のスコープ外の運用作業として別途実施する
- 未有効化の間、および開発環境（`NODE_ENV !== "production"`）では、メールを実送信せずリンクをサーバーログに出力するフォールバックで動作する（`apps/web/src/lib/email.ts`）
- `paritto-auth`（別リポジトリ）：Paritto全体のSSO統合を担う認可サーバー。MCP用OAuth（`docs/design-mcp.md`参照）とは独立した別プロダクトであり、Clipnoteの`users`テーブルとは連携していない
