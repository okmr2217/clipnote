## 0. 用語整理

「コンテンツ／ページ／クリップ」の呼称が曖昧なため、ユーザー向け表示名と内部名を分離して整理する。

| 概念 | DB／コード内部名（変更なし） | ユーザー向け表示名 |
| --- | --- | --- |
| 個別のHTML/Markdown文書 | `pages` | **クリップ**（Clip） |
| 複数クリップの束 | `collections` | **コレクション** |
| 中間テーブル | `collection_pages` | （UI上には露出しない） |
| MCP連携用の鍵 | `api_keys` | **APIキー**（v9で追加） |

- DB・URL（`pages` / `/p/`）は変更しない。UUIDベースで意味を持たないパスのため、表示名変更の影響を受けない。
- UI文言のみ「ページ」→「クリップ」に統一する。

## 1. ドメイン構成

| 用途 | ドメイン |
| --- | --- |
| Web本体（管理画面／公開ページ外枠／LP） | `clipnote.paritto.dev` |

### 実装時の注意点（Cookieスコープ）

親ドメイン`paritto.dev`を共有するため、4章のiframe隔離（別ドメイン配信）による多層防御の効果を実質的に確保するには、**better-authのセッションCookieの`Domain`属性を`clipnote.paritto.dev`というホスト単体にスコープする**（`Domain`属性を省略し、親ドメイン全体に広げない）ことを実装時に必ず確認する。MCPサーバーは4-4節と同様セッションCookieを一切使わない設計のため、この注意点の対象外。

## 2. UI／UXデザイン方針

画面の性質によってデザインシステムを使い分ける。

| 画面 | 採用方針 | 理由 |
| --- | --- | --- |
| `/admin`配下（管理画面、APIキー管理含む） | **shadcn/ui（挙動レイヤー）+ Tailwind CSS、テーマは2-2節のトークンで完全上書き** | フォーカストラップ・キーボード操作・ARIA属性等のアクセシブルな挙動を実装コストなしで得られるため、コンポーネント（Dialog, Table, DropdownMenu等）はshadcn/uiを採用する。ただし既定の見た目（配色・角丸・フォント）はそのまま使わず、Claude Designで確立したデザイントークンで上書きする |
| LP（ランディングページ） | **カスタム（Tailwind CSSでトンマナ設計）** | ユーザー獲得の入口。「AIが生成したHTML/Markdownをそのまま保存・公開できる」という価値をビジュアルで訴求する必要があり、shadcnの定型感では差別化しにくい |
| `/p/[uuid]` `/c/[uuid]`のiframe外枠（ヘッダー／フッター） | LPと同じトンマナのカスタム | 公開URLは第三者に共有される二次的なLPとして機能するため |

iframe内部（ユーザー生成コンテンツそのもの）はデザインシステムの対象外。

### 2-1. デザインの雰囲気

claude.aiに近い、温かみのあるニュートラル基調。テラコッタ〜朱色系のアクセントカラーを1色のみ使用し、余白を広めに取る。ダークモードはMVPでは対応しない（ライトモードのみ）。

### 2-2. デザイントークン

| トークン | 値 | 用途 |
| --- | --- | --- |
| フォント（見出し・本文） | `Plus Jakarta Sans`（サンセリフ） | 見出し・本文とも統一。明朝体・セリフ体は使用しない。見出しは本文より太めのウェイトでコントラストをつける |
| フォント（コード的表示） | `JetBrains Mono` | バイトサイズ表示・URL・APIキー文字列など、等幅が望ましい箇所 |
| アクセントカラー（メイン） | `#C1503A` | 主要なボタン・アクティブ状態・Publicバッジ等 |
| アクセントカラー（濃色バリアント） | `#B5523A` / `#7A3226` | ホバー状態、強調テキスト等 |
| アクセントカラー（淡色バリアント） | `#E4C4B4` | アクセントの背景敷き・淡いハイライト |
| 背景色（クリーム系、明→暗） | `#FBF6F0` → `#F3E9DD` → `#F3E4DA` → `#F1E7DB` → `#E8DCD0` | ページ背景、カード背景、階層による濃淡の使い分け |
| テキストカラー | `#2B2320`（濃）/ `#3D332C` / `#6B5D52` / `#8A7A6D`（淡） | 見出し・本文・補助テキストの階調 |
| 角丸 | 12px（小要素：バッジ・チップ等）〜32px（大きめのカード・ダイアログ）、丸ボタン・アバター等は`999px` | 要素のサイズ・重要度に応じて使い分け |
| 影 | `0 10px 28px -18px rgba(43,35,32,0.18)`（通常のカード等、控えめ）／`0 6px 16px -8px rgba(193,80,58,0.5)`（アクセントカラーを使う要素の強調影） | 強いドロップシャドウは使わない方針を維持 |

## 4. セキュリティ設計

### 4-1. XSS対策：別ドメインiframeによるコンテンツ配信

```
[本オリジン] clipnote.paritto.dev/p/[uuid]
  └─ <iframe src="https://content.clipnote.paritto.dev/[uuid]?t=xxx"
             sandbox="allow-scripts allow-popups allow-modals allow-popups-to-escape-sandbox">
```

> **重要**：この隔離モデルにより、クリップ本文（HTML）に対してスクリプト等の無害化（サニタイズ）処理は行わない。本文中に`<script>`タグや任意のJSが含まれていても、実行コンテキストが親オリジンから完全に分離されているため許容する設計とする。この方針はMCP経由（`upload_page`/`update_page`）で登録されたコンテンツにも同様に適用する。

### 4-2. sandbox属性の内訳

| フラグ | 採用 | 理由 |
| --- | --- | --- |
| `allow-scripts` | ○ | Mermaid等のスクリプト実行に必須 |
| `allow-popups` | ○ | 文書内の外部リンクを新規タブで開く |
| `allow-modals` | ○ | ライブラリ初期化エラー表示等、害は小さい |
| `allow-popups-to-escape-sandbox` | ○ | ポップアップで開いた先に制限を継承させない |
| `allow-same-origin` | ✕（付けない） | Cookie/Storage窃取を防ぐセキュリティの核 |
| `allow-forms` | ✕ | 文書中心の用途では不要 |
| `allow-top-navigation`系 | ✕ | フィッシング対策として付けない |

### 4-3. Hostヘッダー検証

コンテンツ配信エンドポイントで`Host`ヘッダーを検証し、コンテンツ配信ドメイン以外からのアクセスを拒否する。

### 4-4. 認証：署名付き短命トークン（HMAC-SHA256）

別ドメインにはセッションCookieが届かないため、署名付き短命トークン（**有効期限：2分**）で認証する。`content.clipnote.paritto.dev`側は、セッションCookieによるユーザー認証フローを一切持たない（＝ユーザーテーブルへの問い合わせやセッション検証は不要）ステートレスな設計とする。

```
① 本オリジン /p/[uuid] または /c/[uuid] にアクセス
      ↓ セッションCookieで認証確認 + クリップ／コレクションのアクセス権確認
② サーバーサイドでHMAC-SHA256署名付き短命トークンを生成
      ↓ CONTENT_TOKEN_SECRET（両ドメイン共通の環境変数）で署名
③ iframe src="https://content.clipnote.paritto.dev/[uuid]?t=xxx"
      ↓
④ content側でリクエストを処理する
```

トークンの構造：

```
payload = "{userId}:{uuid}:{exp}"
sig     = HMAC-SHA256(payload, CONTENT_TOKEN_SECRET)
token   = base64url("{payload}:{sig}")
```

#### `content.clipnote.paritto.dev`側の処理フロー

```
① Hostヘッダー検証（コンテンツ配信ドメイン以外からのアクセスを拒否）
② HMACトークンの検証（署名の正当性・有効期限・UUID一致確認）
   ← ここはHMAC計算のみで完結し、DBアクセスは不要
③ D1からUUIDで該当するpages行を1件取得
   ← ここはD1への読み取りアクセスが必要（トークン検証とは独立した処理）
④ content_typeに応じて出力：
   - html：pages.contentをそのままレスポンス（Content-Type: text/html）
   - markdown：unified/remark/rehypeでHTMLに変換してからレスポンス
⑤ 本文の無害化（サニタイズ）は行わない（4-1節の方針の通り）
```

UUID一致確認により他クリップのトークン流用を防止。

#### トークンの自動更新

- `/p/[uuid]`・`/c/[uuid]`の親ページ側で、**90秒間隔**で新しいトークンをサーバーから取得し、iframeの`src`属性を新トークンで書き換える（初回表示から2分経過する前に更新する設計）
- 更新はiframeの再読み込みを伴わない形（`src`のクエリパラメータのみ差し替え）を基本とするが、ブラウザ実装によっては同一パス+クエリ変更でも再読み込みが発生しうるため、実装時に挙動を確認する
- トークン取得APIが失敗した場合（セッション切れ等）は、静かに更新を諦め、次回の定期実行を待つ（エラー表示でユーザー体験を損なわない）

### 4-5. 公開設定の扱い（クリップ／コレクション）

| ケース | 挙動 |
| --- | --- |
| privateクリップ（認証済み本人がアクセス） | 通常通りトークン発行 |
| publicクリップ | 認証なしでもトークンを発行 |
| privateコレクション | 認証済み本人のみ`/c/[uuid]`にアクセス可。全所属クリップを一覧表示 |
| publicコレクション（本人以外／未認証がアクセス） | 認証不要で`/c/[uuid]`にアクセス可。**所属クリップのうち`private`のものは一覧から除外** |
| publicコレクション（本人が認証済みでアクセス） | 全所属クリップを一覧表示 |

### 4-6. OGP・シェア時のメタデータ

| 対象 | 挙動 |
| --- | --- |
| publicなクリップ／コレクション | タイトル・説明文を`og:title` / `og:description`として出力。`og:image`は当面固定のブランド画像（Clipnoteのロゴ等）を使用 |
| privateなクリップ／コレクション | OGPタグを一般的な固定文言のみにし、タイトルや説明などクリップ固有の情報は出力しない |

将来、10章のスクリーンショット生成機能が実装され次第、`og:image`を動的なプレビュー画像に差し替える段階的対応とする。

### 4-7. MCPサーバーの認証（v9で追加）

MCPサーバー（`mcp.clipnote.paritto.dev`）は上記のセッションCookie・HMACトークンいずれとも異なる、**APIキー方式**の認証を用いる。詳細は8章（APIキー管理画面）・13章（MCPサーバー設計）を参照。

### 4-8. セキュリティまとめ

| 懸念 | 対策 |
| --- | --- |
| XSS（悪意あるHTMLのスクリプト実行） | iframe別ドメインサーブで親のCookie/Storageを隔離（本文自体の無害化は行わない） |
| iframe srcの書き換え | Hostヘッダー検証でブロック |
| 別ドメインでの認証 | HMAC-SHA256署名付き短命トークン（DBアクセスなしで検証） |
| 親ドメイン共有によるCookie漏出リスク | セッションCookieの`Domain`属性をホスト単体にスコープ |
| UUIDが漏れても非公開クリップを閲覧できる | トークンなしアクセスを拒否 |
| トークンの流用 | トークン内のUUIDと対象クリップのUUIDを一致確認 |
| 公開コレクション経由で非公開クリップの存在が露見する | 一覧そのものから除外（存在の痕跡を残さない） |
| 公開コレクション経由で非公開クリップの存在がOGP等から露見する | privateなコンテンツの固有情報をOGPに出力しない |
| 長時間閲覧時のトークン失効 | iframeの定期的な自動更新 |
| MCP経由での不正アクセス（v9で追加） | APIキーはハッシュ化して保存、Bearerトークンとして検証、他ユーザーのクリップへのアクセスは権限エラーと未存在エラーを区別せず拒否 |

## 5. コンテンツバリデーション

セキュリティ目的ではなく、UX・データ整合性・インフラコスト管理を目的とする。管理画面経由・MCP経由（`upload_page`/`update_page`）いずれも共通のバリデーション関数を通す。

### 5-1. 形式（HTML/Markdown）の妥当性

| チェック内容 | 扱い |
| --- | --- |
| 完全なHTML文書構造（`<html>`/`<body>`必須） | 要求しない（AI生成の断片的なマークアップを許容する） |
| タグの閉じ忘れなどの構文エラー | チェックしない（ブラウザの寛容なパースに委ねる） |
| Markdownとしての妥当性 | チェックしない |
| 空文字列でないか | チェックする |
| 有効なUTF-8か | チェックする |
| 形式の決定（管理画面のみ） | ユーザーによる手動選択は行わない。ファイル読み込み時は拡張子（`.html`/`.htm`→HTML、`.md`/`.markdown`/`.txt`→Markdown）を優先し、貼り付け・未対応拡張子の場合は本文にHTMLタグらしき記述が含まれるかで判定する。MCP経由は`content_type`を呼び出し側が明示するため自動判定は行わない |

### 5-2. データサイズの上限

| 項目 | 値 | 備考 |
| --- | --- | --- |
| 1クリップ（1バージョン）あたりの本文サイズ上限 | **1MB（1,048,576 bytes）** | Cloudflare D1の行サイズ上限2MBに対し安全マージンを確保 |
| 判定基準 | バイト数（UTF-8エンコード後） | 文字数ではなくバイト数で判定 |
| バージョン10件保持時の1クリップあたり最大ストレージ | 約10MB | 11章の`page_versions`参照 |

- クライアント側（管理画面）は本文確定時に上限バイト数を判定し、超過している場合はエラーメッセージで差し戻す（確定表示のカードには常時のバイト数表示は行わない。5-4節・6-2節参照）
- サーバー側でも必ず再チェックする（管理画面・MCP経由共通）

### 5-3. ファイル読み込み時の追加チェック（管理画面のみ）

- 拡張子が`.html` `.htm` `.md` `.markdown` `.txt`以外の場合は警告
- `File.size`を用いて、実際にテキストとして読み込む前にサイズ上限を事前チェックする
- 文字化け検知：U+FFFD等の異常値が一定割合以上含まれる場合、UTF-8確認の警告を表示（保存はブロックしない）

### 5-4. タイトルの自動取得（新規クリップ登録のみ）

本文確定時（貼り付け・ファイル読み込み共通）に、タイトル欄が未入力（ユーザーが一度も編集していない）であれば自動反映する。一度でも手動編集した場合は上書きしない。取得できたタイトル候補は確定表示カード内にも表示する（6-2節参照。バイト数の代わりにこちらを表示する）。コンテンツ更新ダイアログはタイトルを変更しない仕様（6-4節）のため対象外。

優先順位は「本文から抽出したタイトル → ファイル名（拡張子除去） → 反映しない（空のまま手動入力）」。AI生成コンテンツは断片的なファイル名より本文中のタイトルの方が説明的なため、本文からの抽出を優先する。

| 形式 | 抽出方法 |
| --- | --- |
| HTML | `<title>`タグのテキスト。無ければ最初の`<h1>`のテキスト |
| Markdown | 本文先頭の`# 見出し`（H1）のみ。見出し以外の先頭行（表・コードブロックの断片等）はタイトル扱いにしない（誤検知防止のためフォールバックしない） |

抽出したタイトルが120文字を超える場合は切り詰める。

## 6. 画面設計：クリップ管理

### 6-1. クリップ一覧（`/admin`）

**デスクトップ（`md`以上）：テーブル形式**

| 表示列 | 内容 |
| --- | --- |
| 形式バッジ | `HTML` / `MD` |
| タイトル | クリックでプレビューを新規タブで開く |
| 公開設定 | バッジ。クリックでその場でトグル（即時反映） |
| 所属コレクション | チップ表示（複数可） |
| 更新日時 | デフォルトソート軸 |
| 公開URLコピー | Publicなクリップの行に常時表示 |
| 操作 | プレビュー／メタデータ編集／コンテンツ更新／更新履歴／削除（オーバーフローメニュー） |

**モバイル（`md`未満）：カード形式**

```
┌───────────────────────────────┐
│ [HTML] ● Public                 │
│ 今日のAI議事録まとめ               │
│ コレクション: 議事録 / 仕事メモ      │
│ 更新: 2026-08-04                 │
│                                 │
│ [ 🔗コピー ] [ プレビュー ] [ ⋯ ]  │
└───────────────────────────────┘
```

将来検討：一覧アイテムへのサムネイル／プレビュー画像表示（11章参照）。

### 6-2. 新規クリップ登録：ダイアログ

本文入力は「入力待ち」→「確定表示」の2段階UIとする。入力待ち状態では「テキストを貼り付け」と「ファイルをアップロード」を別ブロックに分けて表示し、それぞれに説明文を添える。貼り付け欄は他の入力欄（タイトル等）と同じ見た目・高さの1行テキストフィールドとし、複数行貼り付け時は内部スクロールで保持する（値そのものは改行を含む全文を保持し、表示上だけ縮めている）。確定後は形式・ファイル名（または「貼り付けされたHTML/マークダウン」）・取得したタイトル候補（あれば）をカード状に表示する。形式のユーザーによる手動選択は行わない（5-1節参照）。バイト数は確定表示カードには常時表示しない（5-2節参照。上限超過時は確定時のエラーメッセージで示す）。

```
┌─────────────────────────────────────┐  入力待ち
│ 新規クリップ                           │
├─────────────────────────────────────┤
│ テキストを貼り付け                       │
│ AIとの会話などで生成したHTML/Markdownを  │
│ そのまま貼り付けてください。形式は自動で   │
│ 判定されます。                          │
│ ┌───────────────────────────────┐  │
│ │ ここに貼り付け（他の入力欄と同じ高さ） │  │
│ └───────────────────────────────┘  │
│                              [確定]   │  ← 本文入力中のみ表示
│                 ── または ──          │
│ ┌ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┐  │
│ │ ファイルをアップロード [ファイルを選択] │  │
│ │ ドラッグ&ドロップ、または選択してくださ │  │
│ │ い（.html/.md/.txt等）。ブラウザ内で   │  │
│ │ のみ読み込まれ、送信されません          │  │
│ └ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ─ ┘  │
│                                       │
│ タイトル: [______________]            │
│ 公開設定: ○ Private ● Public          │
│ コレクション: [ 複数選択 ▾ ]（任意）     │
│                                       │
│                  [ キャンセル ] [ 登録 ]│
└─────────────────────────────────────┘

┌─────────────────────────────────┐  確定後
│ 新規クリップ                       │
├─────────────────────────────────┤
│ ┌───────────────────────────┐   │
│ │ [HTML] report.html            │   │
│ │ Q3 Sales Report    [変更する] │   │  ← 取得したタイトル候補
│ └───────────────────────────┘   │
│                                   │
│ タイトル: [______________]        │
│ 公開設定: ○ Private ● Public      │
│ コレクション: [ 複数選択 ▾ ]（任意）│
│                                   │
│              [ キャンセル ] [ 登録 ]│
└─────────────────────────────────┘
```

貼り付けは、テキストエリアへのペースト直後に自動で確定表示へ切り替える。ファイルはサーバーへアップロードしない。`File.text()`でクライアント側のみでファイル内容を読み取り、本文へ反映し、タイトル候補（5-4節参照）をタイトル初期値に反映する。サーバーへ送信するのは、貼り付け・ファイルいずれの経路でも本文の文字列＋メタデータのみ。「変更する」で入力待ち状態へ戻り、本文を空にして再入力できる。

### 6-4. コンテンツ更新：破壊的操作として分離

6-2節と同じ入力UIを再利用しつつ、次の点で新規登録と区別する。

- ダイアログタイトルを「クリップ本文の差し替え」のように明示
- 警告文：「既存の本文を上書きします。この操作は更新履歴として記録され、後から復元・ダウンロードできます」
- 現在の本文と新しい本文のサイズ差分を表示
- タイトル・公開設定・所属コレクションは変更されない旨を明記
- 実行ボタンは警告色（`destructive`バリアント）

内部処理：更新前の本文を`page_versions`へ退避してから`pages.content`を更新する（12-2節参照）。この処理はMCP経由の`update_page`（13章）とも共有ロジックとして実装する。

### 6-5. 更新履歴・バージョンの復元／ダウンロード

`/admin/pages/[uuid]`から辿れる。差分（diff）表示は行わず、全文プレビューでの確認ベースとする。

**現在のバージョンにも過去のバージョンにも「ダウンロード」を提供する。復元は過去のバージョンにのみ提供する。**

```
┌─────────────────────────────────┐
│ 更新履歴                          │
├─────────────────────────────────┤
│ ● 現在のバージョン (v5)             │
│   2026-08-04 10:20    [ダウンロード] │
│                                   │
│ ○ v4  2026-08-03 18:02  [プレビュー][ダウンロード][復元] │
│ ○ v3  2026-08-01 09:15  [プレビュー][ダウンロード][復元] │
│ ○ v2  2026-07-30 14:40  [プレビュー][ダウンロード][復元] │
│ ○ v1  2026-07-28 11:00  [プレビュー][ダウンロード][復元] │
│                                   │
│ （直近10件のみ保持）                 │
└─────────────────────────────────┘
```

- 「プレビュー」：そのバージョンの内容を別ドメインiframeで簡易レンダリング表示
- 「ダウンロード」：クライアント側でBlob生成しファイル保存。サーバー通信不要。ファイル名は`{タイトル}_v{番号}.{html|md}`形式（現在のバージョンは`{タイトル}.{html|md}`）
- 「復元」：実行すると、復元前の現在の内容も新しいバージョンとして履歴に退避してから上書きする（＝復元自体も1回の更新として記録される）
- ダウンロードは無害な操作のため確認ダイアログ不要（10章参照）

## 7. 画面設計：コレクション管理

### 7-1. コレクション一覧（`/admin/collections`）

クリップ一覧（6-1節）と対称的な構成にするが、以下の点はクリップと異なる（v9で確定）。

**デスクトップ（`md`以上）：テーブル形式**

| 表示列 | 内容 |
| --- | --- |
| コレクション名 | クリックで**詳細画面へ遷移**（同タブ）。クリップ一覧の「クリック→プレビュー別タブ」とは意図的に非対称。コレクション単体のプレビューという概念がなく、詳細画面に入るのが自然な動線のため |
| 説明 | 1行省略表示。**未入力の場合は「説明なし」を淡色プレースホルダーで表示**（v9で確定。空欄のままにしない） |
| 公開設定 | バッジ、クリックでトグル |
| 所属クリップ数 | バッジ表示（例：「3件」）。**0件のコレクションも特別な視覚処理はせず通常表示**（v9で確定） |
| 更新日時 | ソート軸 |
| 公開URLコピー | Publicなコレクションに常時表示 |

**オーバーフローメニューの項目（v9で確定）**：「編集」「削除」の**2項目のみ**。クリップのような「コンテンツ更新」「更新履歴」に相当する概念がコレクションにはないため。

**モバイル（`md`未満）：カード形式**（クリップ一覧のカードと同様の構成）

**新規作成フロー（v9で変更）**：「＋ 新規コレクション」から名前・説明・公開設定のみの軽量ダイアログ。**作成完了後は自動的に詳細画面（7-2節）へ遷移し、その画面上で「クリップを追加」ダイアログ（7-4節）を開いた状態にする。** 作成ダイアログ自体に入力項目を追加するのではなく、次のアクションへの導線を画面遷移で担保する設計とする。

### 7-2. コレクション詳細（`/admin/collections/[uuid]`）

```
┌─────────────────────────────────────┐
│ コレクション: 議事録まとめ                │
│ 説明: 週次AI議事録をまとめたもの            │
│ 公開設定: ● Public   [情報を編集]          │
│ [🔗 公開URLをコピー]  [公開ページで見る ↗]  │  ← v9で追加
├─────────────────────────────────────┤
│                          [+ クリップを追加] │
│ ⠿  [HTML] 今日のAI議事録まとめ      [外す] │
│ ⠿  [MD]   先週の振り返りメモ        [外す] │
│ ⠿  [HTML] プロジェクトA議事録       [外す] │
└─────────────────────────────────────┘
```

**v9での追加要素**：
- 公開設定が`public`の場合、クリップ一覧と同様に「公開URLコピー」ボタンを表示
- 「公開ページで見る」リンク（`/c/[uuid]`を新規タブで開く）を追加。所有者本人は非公開クリップも含め全件見える（4-5節）ため実際の来訪者視点そのものではないが、レイアウト確認用として有用

クリップが0件の場合は空状態表示（「まだクリップがありません。［＋ クリップを追加］」）とする。クリップ件数が多い場合でもページネーションは実装しない（通常のスクロールで対応。MVP規模での運用を想定）。

### 7-3. 並び替えUX

デスクトップとモバイルで実装方式を分ける。

| 環境 | 方式 | 理由 |
| --- | --- | --- |
| デスクトップ（`md`以上） | ドラッグ&ドロップ（ドラッグハンドル`⠿`付き） | マウス操作なら誤操作が起きにくく直感的 |
| モバイル（`md`未満） | 並び替えモード＋上下移動ボタン | タッチドラッグはスクロールと衝突しやすい。明示的な「並び替えモード」に入り`↑` `↓`ボタンで1件ずつ動かす |

**デスクトップの挙動詳細（v9で追加）**：
- ドラッグ中、ドロップ予定位置に**プレースホルダー（挿入位置を示す線）**を表示する
- ドロップ確定時に、影響を受けた行の`sort_order`をまとめて1回のAPIコールとして送信する（書き込み回数を抑制）

**モバイルの挙動詳細（v9で確定）**：

```
モバイル（並び替えモード）
┌───────────────────────────────┐
│ 並び替え中            [完了]     │
├───────────────────────────────┤
│ [HTML] 今日のAI議事録まとめ  ↑ ↓  │
│ [MD]   先週の振り返りメモ    ↑ ↓  │
└───────────────────────────────┘
```

- 並び替えモード中の`↑` `↓`ボタンによる移動は、**サーバーへは送信せずローカル状態のみ即時反映**する
- 「完了」ボタンを押した時点で、影響を受けた行の`sort_order`をまとめて1回のAPIコールとして送信する
- **「完了」を押さずに画面を離れた場合（戻る操作・別画面への遷移など）は、変更を破棄し元の順序に戻す**（サーバーへの送信は一切行わない）。実装上は、並び替えモード中はローカルstate（メモリ上のコピー）でのみ順序を保持し、実際のリスト表示に反映しているデータとは分離しておく
- 実装ライブラリは`dnd-kit`を推奨（キーボード操作にも対応しアクセシビリティ面で有利）
- 並び替えモード中は、プレビュー等の通常操作を無効化する

### 7-4. クリップの追加

```
┌─────────────────────────────────┐
│ クリップを追加                     │
├─────────────────────────────────┤
│ 検索: [______________]             │
│                                   │
│ ☑ [HTML] 今日のAI議事録まとめ         │
│ ☐ [MD]   先週の振り返りメモ           │
```

## 9. 削除時のカスケード挙動

| 削除対象 | 影響範囲 |
| --- | --- |
| クリップを削除 | `page_versions`（履歴）も連動削除。所属していた全コレクションの`collection_pages`からも自動的に外れる（コレクション自体は残る） |
| コレクションを削除 | `collection_pages`の関連付けのみ削除。**所属していたクリップ自体は削除されない** |
| ユーザーを削除（想定上） | 所有する`pages`・`collections`・`api_keys`も連動削除（`ON DELETE CASCADE`） |

DB制約としては、`collection_pages.page_id`・`collection_pages.collection_id`・`page_versions.page_id`・`api_keys.user_id`に`ON DELETE CASCADE`を設定し、アプリケーション側で個別に削除処理を書かずに整合性を保つ。

コレクション削除時の確認ダイアログには「所属していたクリップ自体は削除されません」という文言を明記し、誤解を防ぐ（10章参照）。

## 10. 確認ダイアログの一貫した基準

破壊性・復元可能性に応じて、確認ダイアログの要否を統一する。

| 操作 | 確認ダイアログ | 理由 |
| --- | --- | --- |
| 公開設定のトグル | 不要（即時反映） | 何度でも戻せる |
| メタデータ編集の保存 | 不要 | 低リスク |
| コレクションから「外す」 | 不要 | クリップ自体は残る |
| バージョンのダウンロード | 不要 | 状態変更を伴わない無害な操作 |
| コンテンツ更新（本文差し替え） | **必要**（警告文＋サイズ差分表示） | 復元可能だが心理的インパクトが大きい |
| バージョンの復元 | **必要**（「vNの内容で上書きします」の確認） | 現在の内容を意図せず失うと感じやすい |
| クリップ削除 | **必要** | 完全に元に戻せない（バージョン履歴ごと消える） |
| コレクション削除 | **必要**（「クリップ自体は消えません」を明記） | 誤解されやすいため文言が重要 |
| APIキーの失効（v9で追加） | **必要**（「連携が利用できなくなる」旨を明記） | 再発行が必要になり元に戻せない |

## 12. データモデル（詳細）

### `users`テーブル（better-auth管理）

better-authが管理する標準スキーマを利用（email/password認証）。

### `pages`テーブル

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| user_id | uuid | FK → users |
| title | text | クリップタイトル |
| content | text | コンテンツ本体（現在のバージョン） |
| content_type | enum | `html` / `markdown` |
| visibility | enum | `private` / `public` |
| created_at | timestamp | |
| updated_at | timestamp | |

> `content`のサイズ上限：1MB（1,048,576 bytes、UTF-8）。アプリケーション側でバリデーション（5-2節）。管理画面・MCP経由共通。

### `collections`テーブル

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| user_id | uuid | FK → users |
| name | text | コレクション名 |
| description | text | コレクションの説明（任意） |
| visibility | enum | `private` / `public` |
| created_at | timestamp | |
| updated_at | timestamp | |

### `collection_pages`テーブル（中間テーブル）

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| collection_id | uuid | FK → collections（`ON DELETE CASCADE`） |
| page_id | uuid | FK → pages（`ON DELETE CASCADE`） |
| sort_order | int | コレクション内の表示順（DnD／上下ボタンで操作） |
| created_at | timestamp | |

### `page_versions`テーブル

コンテンツ更新時に、更新前の内容を退避するためのバージョン履歴テーブル。ダウンロード機能・復元機能の両方で参照される。管理画面経由・MCP経由（`update_page`）いずれの更新でも同じロジックで退避する。

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| page_id | uuid | FK → pages（`ON DELETE CASCADE`） |
| content | text | その時点でのコンテンツ本体 |
| content_type | enum | `html` / `markdown` |
| version_number | int | 1から始まる連番（page_id内で一意） |
| created_at | timestamp | このバージョンが作られた日時 |

**運用方針**：

- `pages.content`は常に「現在のバージョン」を保持する
- 更新の流れ：①更新前の`pages.content`を`page_versions`へ退避（新しい`version_number`でINSERT）→ ②`pages.content`を新しい内容でUPDATE
- 復元の流れ：①復元前の現在の内容を`page_versions`へ退避 → ②選択したバージョンの内容で`pages.content`をUPDATE（＝復元も1回の更新として履歴に残る）
- ダウンロードの流れ：現在のバージョンは`pages.content`、過去のバージョンは該当行の`content`を、いずれもクライアント側でBlob化してファイル保存（サーバー側の追加処理は不要）
- 保持件数：直近10件を上限とし、超過分は古いものから削除する
- タイトル等の軽量なメタデータはバージョン管理の対象外（本文のみ）

### `api_keys`テーブル（v9で新規追加）

| カラム | 型 | 内容 |
| --- | --- | --- |
| id | uuid | PK |
| user_id | uuid | FK → users（`ON DELETE CASCADE`） |
| name | text | ユーザーが付けた名前（例:「Claude Desktop用」）、必須 |
| key_hash | text | APIキーのハッシュ値（bcrypt等）。生キーは保存しない |
| key_prefix | text | 一覧でのマスク表示用（先頭数文字＋末尾4文字を保持、または生成時に別途保持） |
| created_at | timestamp | |
| last_used_at | timestamp | nullable。MCPリクエスト認証成功のたびに更新 |

**運用方針**：
- キーのフォーマットは`cn_live_{ランダム文字列32文字程度}`（暗号学的に安全な乱数で生成）
- 発行時のみ生のキー全文をレスポンスで返す。以降はハッシュ照合のみで検証し、平文は保持しない
- スコープ分け（read/write）は設けず、全キー同一権限（将来検討、11章参照）

## 13. MCPサーバー設計（v9で新規追加）

### 13-1. 概要

`mcp.clipnote.paritto.dev`で稼働するMCPサーバー。ClaudeなどのMCP対応クライアントから、Clipnoteのクリップを直接参照・登録・更新できるようにする。認証はAPIキー方式（8章・4-7節）。

### 13-2. 技術構成

- Honoベースの軽量Worker（`apps/content`と同じ方針。Next.js/Reactランタイムは使わない。単純なリクエスト処理のみのため、バンドルサイズ・コールドスタートを最小化する）
- トランスポート：Streamable HTTP（MCP TypeScript SDKのHTTPトランスポートを利用）
- `packages/db`を通じてD1へアクセスし、既存のクリップ・コレクションのクエリ層・バリデーションロジック・`page_versions`退避ロジックを管理画面（web）と共有する

### 13-3. 認証フロー

```
① クライアントがリクエストヘッダーに Authorization: Bearer {APIキー} を付与
② サーバー側でキーをハッシュ化し、api_keys.key_hash と照合してuser_idを特定
③ 認証成功時、該当行の last_used_at を更新
④ 認証失敗時はMCPのエラーレスポンスとして返す
```

APIキーのハッシュ照合ロジックは、Web側（管理画面での発行）とMCP側（検証）の両方から参照するため、`packages/db`または新規`packages/auth`として共有パッケージ化する（設計書12-2節の「2つ以上のappsから参照されるものだけpackages化する」方針に準拠）。

### 13-4. ツール定義

#### `list_pages`

- 引数：`query`（タイトル部分一致検索、任意・省略可）
- 返り値：該当ユーザーのクリップ一覧。各項目は`uuid`・`title`・`content_type`・`visibility`・`updated_at`（本文は含めない）

#### `get_page`

- 引数：`uuid`（必須）
- 返り値：`uuid`・`title`・`content`（本文）・`content_type`・`visibility`・`updated_at`
- 対象クリップが存在しない、または他ユーザーのものである場合はエラー（存在の有無を区別しないメッセージにし、他ユーザーのクリップの存在を推測されないようにする）

#### `upload_page`

- 引数：
  - `content`（必須）
  - `content_type`（`html` / `markdown`、必須。自動判定はしない）
  - `title`（必須）
  - `visibility`（`private` / `public`、省略時は`private`）
- コレクションへの割当引数は**持たせない**（MVPの範囲外。管理画面から手動で割り当てる運用、11章参照）
- バリデーション：空文字列・不正UTF-8の拒否、1MB上限チェックを管理画面と共通の関数で実施（5章参照）
- 返り値：`uuid`、公開URL（`https://clipnote.paritto.dev/p/{uuid}`）

#### `update_page`

- 引数：`uuid`（必須）、`content`（必須、全文差し替え）
- 内部処理：更新前の本文を`page_versions`へ退避してから`pages.content`を更新（6-4節・12章の`page_versions`運用方針と同じロジックを共有関数として再利用する）
- バリデーションは`upload_page`と共通
- 対象クリップが他ユーザーのものである場合はエラー
- 返り値：`uuid`、公開URL

### 13-5. エラーハンドリング

| ケース | 扱い |
| --- | --- |
| APIキー無効・失効済み | 認証エラーとして返す |
| 対象クリップが存在しない／他ユーザー所有 | 権限エラーと未存在エラーを区別しないメッセージ |
| 本文サイズ超過 | 上限バイト数と現在のバイト数を含めたエラーメッセージ |
| 空文字列・不正UTF-8 | バリデーションエラーメッセージ |

### 13-6. スコープ外（次フェーズ以降）

- クリップの削除、コレクションの作成・編集・クリップの追加操作（11章参照）
- APIキーのスコープ分け（read/write）

## 14. モノレポ構成

`apps/`（デプロイされる実行単位）と`packages/`（共有ライブラリ）を分ける構成とする。

```
clipnote/
├── apps/
│   ├── web/               # メイン Next.js アプリ（clipnote.paritto.dev）
│   ├── content/            # コンテンツ配信 Worker（content.clipnote.paritto.dev）
│   └── mcp/                # MCPサーバー Worker（mcp.clipnote.paritto.dev、v9で実装対象に）
├── packages/
│   ├── db/                  # D1スキーマ・マイグレーション・クエリ層
│   ├── content-token/        # HMAC署名・検証ロジック（web/contentで共有）
│   └── auth/                 # APIキーのハッシュ生成・照合ロジック（web/mcpで共有、v9で追加検討）
├── docs/
│   ├── requirements.md
│   └── design.md
├── package.json
└── pnpm-workspace.yaml
```

### 14-1. `apps/`の内訳

| フォルダ | 収める内容 | 理由 |
| --- | --- | --- |
| `apps/web` | 管理画面（クリップ・コレクション・APIキー管理）・LP・`/p/` `/c/`の外枠（Next.js全体） | ドメイン設計（1章）と1対1対応させる |
| `apps/content` | コンテンツ配信専用の軽量Worker（Next.jsではなくHono等の軽量ルーターを使用） | トークン検証はステートレス（4-4節）だが、コンテンツ本体の取得にはD1読み取りアクセスが必要。Next.js/Reactランタイムのオーバーヘッドを避け、バンドルサイズ・コールドスタートを最小化する。Markdown→HTML変換（unified/remark/rehype）もこのWorker内で行う |
| `apps/mcp` | MCPサーバー（v9で実装。13章参照） | `apps/content`と同じ理由でHonoベースの軽量構成にする |

### 14-2. `packages/`の内訳と切り出し方針

「2つ以上の`apps`から参照されるもの」だけを`packages/`に切り出す方針とし、過剰分割にならないようにする。

| パッケージ | 収める内容 | 理由 |
| --- | --- | --- |
| `packages/db` | D1スキーマ定義・マイグレーション（12章のテーブル定義） | `web`・`content`・`mcp`のすべてがD1への読み取り・書き込みを行うため共有パッケージ化する |
| `packages/content-token` | HMAC-SHA256のトークン生成・検証ロジック（4-4節の`payload`構造） | `web`（生成）と`content`（検証）の両方が同じロジックを持つ必要がある。2箇所に別々実装すると片方だけ仕様変更が漏れる事故に繋がるため、必ず共有パッケージとして切り出す |
| `packages/auth`（v9で追加検討） | APIキーのハッシュ生成・照合ロジック（8章・13-3節） | `web`（発行時のハッシュ生成）と`mcp`（検証時のハッシュ照合）の両方が同じロジックを持つ必要がある。`content-token`と同じ理由で共有パッケージ化する |

shadcn/uiのコンポーネント等、現時点で`web`のみが使うものは`apps/web`内に置き、無理に`packages/ui`のような形で切り出さない。

### 14-3. ツール構成

`pnpm workspaces` + `turborepo`の組み合わせを推奨する。`turbo.json`でapp単位のビルド・デプロイタスクを分離できるため、「`mcp`だけ再デプロイする」といった単位でのタスク実行に対応しやすい。
